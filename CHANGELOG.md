## Todas as decisões, por componente

### Accordion

- Um componente só (Accordion) cobre tanto 'item único' quanto 'vários agrupados', em vez de um átomo Collapsible separado + um Accordion que o envolve. Motivo: o comportamento real (cabeçalho clicável, aria-expanded, painel que expande/colapsa, animação de altura) é idêntico nos dois casos — só muda se há 1 ou N items no array, e se mode importa (só faz diferença com 2+). Duas APIs pro mesmo padrão visual criariam a mesma duplicação que o harness evita em outros lugares (ex.: Datatable não tem um sistema de column.type separado por tipo de célula).
- Controlado via openKeys (array) + onChange, mesmo padrão de Tabs value/onChange — mas aqui é array em vez de valor único, porque multiple precisa representar 'vários abertos ao mesmo tempo'. O próprio Accordion calcula o próximo array (respeitando mode) e entrega pronto pro onChange — o consumidor nunca implementa a lógica de 'fechar os outros' por fora, mesmo racional de Datatable calcular sortMode/paginationMode internamente antes de notificar via callback.
- mode='multiple' como default (não 'single') — abrir mais de um item ao mesmo tempo é o comportamento mais permissivo e não surpreende o usuário; single é opt-in pra quando o consumidor quer forçar exclusividade (ex.: FAQ onde só uma resposta deveria ficar visível por vez).
- Sem navegação por seta entre cabeçalhos (diferente de Tabs) — Accordion não é uma seleção mutuamente exclusiva como tablist, é uma lista de botões independentes; roving tabindex adicionaria complexidade sem um requisito real do padrão ARIA Accordion (que, ao contrário do ARIA Tabs, não pede isso).
- Animação de altura via CSS grid-template-rows (0fr fechado → 1fr aberto) na própria linha do grid do painel, em vez de max-height fixo ou JS medindo scrollHeight — funciona com conteúdo de altura variável/dinâmica sem gambiarra de altura hardcoded nem ResizeObserver.
- Painel sempre montado no DOM (visualmente colapsado via CSS), nunca desmontado enquanto fechado — mesmo racional do TabPanel de Tabs: preserva scroll/estado de formulário dentro do conteúdo entre um toggle e outro.
- Ícone caret-down (já existente no registro do Icon) gira 180° via CSS transform conforme o estado aberto/fechado, em vez de trocar entre caret-down/caret-up — evita duas entradas de ícone pra comunicar a mesma coisa, mesma técnica já usada implicitamente noutros togglers do harness (ex.: nenhum componente troca o glyph do Icon só pra indicar orientação quando rotacionar resolve).
- BUG REAL corrigido em revisão pedida pelo usuário — o cabeçalho usava type-style.texto-p (14px) com font-weight:700 hardcoded (não um token real, um mix improvisado de tamanho normal + peso manual). Isso destoava do resto do harness, onde todo 'título clicável/de destaque' equivalente (título de Modal, de Drawer, de Alert, nome em Avatar, título de EmptyState) usa consistentemente type-style.texto-m-forte (16px/700, via variável, não peso hardcoded). Corrigido pra texto-m-forte no cabeçalho — o painel de conteúdo continua em texto-p (14px/400), que é o tamanho de corpo de texto correto e já estava certo.

### ActionCard

- Nasceu da análise de sistemas legados (analise-sistemas-legados.md, item 1.4) — grade 3×3 de cartões de ação no 'Painel de supervisão' de um sistema de corretor, cada um com ícone colorido, 2 ícones utilitários, título, descrição, status opcional e 1-2 botões.
- primaryVariant é uma prop exposta (não fixa por iconTone) — decisão do agente: nos prints legados, a cor do botão principal nem sempre acompanhava a cor do ícone (ex.: 'Cancelar contratos em lote' tinha ícone vermelho mas botão escuro/neutro, não vermelho) — forçar uma correspondência automática icone→botão inventaria uma regra que os prints reais não seguem. Deixar como prop livre (reaproveitando ButtonVariant) é mais simples e não assume um padrão que não existe.
- status é um objeto opcional { label, active }, não duas props separadas (statusLabel/statusActive) — os dois sempre andam juntos (não faz sentido ter só um dos dois), mesmo racional de objeto único já usado em DatatableColumn/TimelineItem pra dados que sempre aparecem em conjunto.
- onInfo/onSettings são independentes e opcionais — um ActionCard pode não ter nenhum, só um, ou os dois utilitários. Ausência = ícone correspondente simplesmente não renderiza (em vez de renderizar desabilitado), mesmo racional de badgeLabel ausente no SelectableCard não renderizar um Badge vazio.
- iconTone só tem 2 opções (default/destructive), não o enum inteiro de status do Badge — decisão do agente: o ícone do ActionCard comunica 'isto é uma ação seguro/normal' vs 'isto é uma ação de risco', uma distinção binária. Se surgir necessidade real de mais tons (ex.: 'ação de aviso'), é decisão nova.
- Reaproveita o átomo Card (padding='medium') como superfície externa, em vez de estilizar um <div> do zero — ActionCard é fundamentalmente uma composição de Card+Icon+Button com um layout de conteúdo fixo, não uma superfície nova.
- Novo nome de ícone 'gear' adicionado ao registro do Icon (icon.contract.json: 'cresce sob demanda de um consumidor real') — ActionCard é o primeiro consumidor real que precisa de um ícone de configuração; nenhum ícone existente no registro cobria esse caso.
- AJUSTADO a pedido do usuário — ícone principal deixou de ter um fundo/badge colorido (quadrado com cantos arredondados + ícone branco dentro) e virou um ícone simples, colorido diretamente (sem caixa ao redor). Motivo explícito: 'os ícones na parte superior esquerda estão muito parecidos com botões, isso pode confundir os usuários'. O badge com fundo sólido tinha a MESMA linguagem visual de um botão iconOnly do harness (fundo colorido + cantos arredondados + ícone branco), então lia como clicável mesmo sendo só decorativo — removido o fundo, o ícone agora é só o glifo colorido (ou cinza, via iconTone='neutral', nova opção — 'podem ser coloridos ou não'), sem nenhuma affordance de botão.
- AJUSTADO a pedido do usuário — novo par de props secondaryVariant/secondaryOutlined, pra viabilizar uma versão do ActionCard com DOIS botões reais no rodapé (não só botão principal + link secundário). secondaryVariant reaproveita o mesmo ButtonVariant de primaryVariant (nenhum enum novo) — default 'link' preserva o comportamento original (rodapé com botão sólido + texto em link), mas setar secondaryVariant='neutral' + secondaryOutlined=true reproduz exatamente o par 'Cancelar (contornado) / Confirmar (sólido)' que já é o padrão estabelecido nos Modals de confirmação do Datatable (ver datatable.contract.json) — ActionCard não inventou um layout novo de dois-botões, só passou a permitir o mesmo padrão já validado em outro lugar do harness.
- AJUSTADO a pedido do usuário — as ações (botão principal + secundário, se houver) agora ficam SEMPRE ancoradas no fim do card, mesmo quando o card é esticado além da altura do próprio conteúdo (ex.: grid CSS com align-items:stretch padrão, cards vizinhos com mais conteúdo/mais alto na mesma linha). Pedido explícito: 'o botão ou os botões de ação devem ficar alinhados no bottom criando o espaço em branco entre o texto e o botão' — em vez do espaço extra sobrar embaixo dos botões (like antes). Implementado envolvendo TODO o conteúdo do card (cabeçalho até ações) num wrapper `display:flex; flex-direction:column; height:100%` dentro do Card, com `.actions { margin-top: auto; padding-top: espaco-m }` — o padding-top garante um espaçamento mínimo mesmo sem sobra de altura, e o margin-top:auto consome qualquer altura extra empurrando as ações pro fim. Confirmado no navegador via medição de posição (getBoundingClientRect): dois ActionCard na mesma linha da grade, um com menos conteúdo que o outro, com os botões alinhados no mesmo Y.
- REVISADO — o ícone principal voltou a ter um círculo de fundo ao redor (que tinha sido removido no ajuste anterior por lembrar um botão), mas agora TRANSLÚCIDO/bem claro na mesma cor do ícone (acao-primaria-transparente/acao-destrutiva-transparente, os mesmos tokens de opacidade 10% já usados como estado 'transparente' das Ações do harness — reaproveitados aqui pela primeira vez fora do contexto de Button/interação), em vez de um fundo SÓLIDO com ícone branco por dentro. Pedido explícito do usuário: 'os ícones da esquerda estão muito sutis... crie uma div redonda ao redor dele, com a cor de fundo na mesma cor do ícone, só que bem clarinha'. Diferença chave que evita reintroduzir o problema anterior ('parece botão'): um fundo sólido + ícone branco imita a aparência de um botão iconOnly preenchido (alto contraste, convite a interação); um fundo translúcido claro com o ícone colorido por cima lê como um selo/indicador decorativo (baixo contraste entre fundo e ícone, sem a assinatura visual 'botão' do resto do harness). Ícone também aumentou de size='medium' (20px) pra size='large' (24px) e ganhou weight='bold' (era 'regular', o peso padrão do Icon) — pedido explícito 'deixe eles um pouquinho maior, com um peso levemente maior também'.

### Alert

- 4 intents (info/success/warning/error) mapeiam direto pras 4 famílias 'Sinalização' que já existem em tokens.json — nenhum token novo de cor foi criado, só trazidos pro tokens.css. As famílias apoio-1/apoio-2 também existem no tokens.json mas não têm significado universal de status (são tons de categoria/marca, não 'isso deu certo/errado') — ficaram fora deste contrato; usar Alert pra 'apoio' não tem semântica clara. Se surgir um caso real, é decisão nova.
- role dinâmica por intent: 'alert' (interrompe, aria-live assertivo) só pra error/warning, que precisam de atenção imediata — ex.: 'usuário ou senha inválidos' depois de um submit. 'status' (aria-live polido) pra info/success, que não devem cortar o que a pessoa está fazendo no meio.
- Contraste testado texto-do-intent CONTRA o fundo tintado do MESMO intent (não contra branco, que seria um teste artificial já que o Alert nunca aparece sobre fundo branco puro): erro 7.32:1 (AAA), sucesso 6.87:1 (AA), aviso 4.90:1 (AA — o mais apertado, não reduzir peso do texto ali), info 6.84:1 (AA).
- Título usa type-style.texto-m-forte (negrito, token de tipografia dedicado que já existe em tokens.json) — não é font-weight cru aplicado por fora.
- dismissible/onDismiss: Alert é 100% controlado, como todo o resto do harness (TextField/value, Checkbox/checked) — não guarda estado próprio de 'estou visível'. onDismiss só avisa; remover da árvore é responsabilidade de quem consome.
- Ícone por intent é fixo (não é uma prop customizável) — info→'info', success→'check-circle', warning→'warning-circle', error→'x-circle', neutral→'info' (mesmo glifo do info, ver decision abaixo) — mantém o registro fechado do Icon e a consistência visual entre todos os usos de Alert no produto.
- REVISADO — contorno (border-color) de info/success/warning/error trocado da cor 'crua' (ex.: borda-erro #eb5757, bem saturada) pra color-mix(in srgb, var(--borda-X) 35%, var(--fundo-X)) — mistura a mesma cor semântica com o próprio fundo tintado do Alert, produzindo um contorno bem mais sutil (mesmo tom, muito menos saturado) sem inventar nenhum token de cor novo. Pedido explícito do usuário ('cores genéricas e sem graça, contorno mais sutil melhoraria'). Mesma técnica (color-mix sobre tokens existentes) já usada em outros lugares do harness (ex.: hover do botão de fechar deste próprio Alert).
- Intent 'neutral' adicionado a pedido do usuário — fundo cinza claro (fundo-secundario) + texto escuro (texto-primario), pra mensagem de contexto sem carga de status (nem erro, nem sucesso, nem aviso, nem info). Ícone reaproveita o glifo de 'info' (só muda a cor, pra icone-secundario) — não existe um glifo 'neutro' que faça sentido ter separado, e a regra de 'ícone nunca é opcional' (a11y.notes) continua valendo. Contorno usa borda-base diretamente (já é um cinza neutro, sem saturação pra suavizar via color-mix como os outros 4 intents).
- AJUSTADO a pedido do usuário — nova prop 'action' opcional ({ label, onAction }), pra casos como Datatable precisar de um Alert com uma ação curta embutida (ver contratos/datatable.contract.json, decisions, colunas ocultas). Renderizada como <button> em texto sublinhado, cor=currentColor (herda a cor de texto do intent ativo, sem token extra) — não é um Button do harness (variant='link') porque Button tem padding/altura pensados pra ficar fora de contexto de texto corrido; aqui a ação precisa ler como parte da frase, não como um controle separado flutuando ao lado. Alert continua 100% controlado: onAction só avisa, quem decide o que fazer (ex.: restaurar colunas) é responsabilidade de quem consome, mesmo racional já usado em onDismiss.

- O último item de 'items' NUNCA renderiza como link, mesmo que venha com href preenchido — href nessa posição é simplesmente ignorado, não é erro (é comum o consumidor montar o array de forma genérica a partir de uma lista de rotas, onde a última rota também tem uma URL válida; forçar o consumidor a lembrar de omitir href só pro último item seria mais fricção do que ajuda). - Itens intermediários reaproveitam o átomo Link inteiro (não um <a> customizado) — herda toda a semântica/contraste/foco já validados em link.contract.json, inclusive underline/estado disabled se algum dia fizer sentido num nível da trilha.
- Separador é Icon 'caret-right' (Phosphor CaretRight, adicionado agora ao registro fechado — Breadcrumb é o primeiro consumidor real, mesma disciplina de crescimento sob demanda já usada nos outros ícones), sempre aria-hidden — a ordem do DOM/<ol> já comunica a hierarquia pra quem usa leitor de tela, o separador visual é redundante pra acessibilidade.
- RESOLVIDO — truncamento de trilhas longas implementado a pedido do usuário. Padrão: primeiro item + reticências (clicáveis, abrem popover) + últimos 2 itens (pai imediato + página atual), a partir de items.length > collapseThreshold (default 3, ou seja, colapsa com 4+ níveis — número literal que o usuário usou como exemplo). collapseThreshold é configurável por instância pra quem tiver uma hierarquia tipicamente mais profunda e não quiser colapsar tão cedo ('podem ser mais, se for interessante e usual').
- Reticências abrem um popover (não um <select> ou navegação inline) com @floating-ui/react — mesmo padrão já usado em Select/Tooltip/Datatable (colunas visíveis, exportação), não introduz uma terceira forma de resolver 'elemento ancorado que não pode sair da viewport'. Sem sombra, só borda, mesma convenção flat do resto do harness.
- RESOLVIDO — bug real reportado: texto dos itens dentro do popover de reticências não herdava a fonte do harness (caía no padrão do navegador). Causa: FloatingPortal renderiza o popover fora da árvore de .list (escapa do <nav>), e Link não tem tipografia própria — depende inteiramente de herdar font-family/size do contexto (ver link.contract.json). Corrigido declarando type-style.texto-p explicitamente em .menu, já que o contexto herdado real (fora do portal) não é mais o do Breadcrumb.
- Sempre mostra EXATAMENTE 2 itens depois das reticências (pai imediato + atual), não 1 — dá contexto de onde a página atual está aninhada sem precisar abrir o popover pra descobrir. Mostrar só a página atual sozinha depois de '...' perderia informação útil que cabe tranquilamente no espaço.
- firstItemIcon é uma prop de nome de ícone (IconName), não fixada em 'house' — pedido explícito do usuário ('pode ser uma casinha ou outro que o usuário escolha'). Sem valor default: a maioria das trilhas não precisa de ícone no primeiro item, forçar um ícone fixo (mesmo que 'house') seria decidir por produtos que talvez não usem esse padrão visual.
- <ol> em vez de <ul> — a ordem dos itens carrega significado hierárquico real (não é uma lista de opções intercambiáveis), mesma lógica que já rege outras decisões de semântica HTML no harness (ex.: Divider usa role=separator explícito em vez de depender de estilo).

Tentativa anterior: usar semantic.texto-secundario (cinza-600, 7.56:1 contra branco, AAA) pro texto/borda, no lugar de acao-sutil-pressionada (cinza-300, 1.47:1, ilegível). Mas medir o contraste ENTRE os dois botões (não cada um contra o branco) mostrou só 2.35:1 de diferença — abaixo do mínimo de 3:1 que o WCAG pede pra distinguir componentes de UI entre si (SC 1.4.11), confirmado visualmente por revisão humana. ### Calendar

- Navegação 'simples' (setas mês anterior/próximo, sempre visíveis) e 'complexa' (pular direto pra outro mês/ano) resolvidas como UMA interação no mesmo componente, não como duas variantes/props: as setas do cabeçalho cobrem o caso comum (navegar 1 mês), e clicar no rótulo 'Mês de Ano' abre um seletor rápido de mês (grade de 12 meses do ano exibido, com setas de ano) pra pular direto quando a data está longe. São complementares, não alternativas — não fazia sentido esconder um dos dois atrás de uma prop.
- Mês/ano exibido (viewYear/viewMonth) e o modo do seletor (dias vs. meses) são estado interno, transiente, NÃO controlado por fora — só value (a data selecionada) é controlada. Inicializado a partir de value (ou 'hoje' se value for null) na primeira renderização, mas não resincroniza automaticamente se value mudar por uma causa externa depois — mesma classe de decisão já usada em Datatable pra editingRowKey/openFilterColumnKey: é estado de navegação/UI, não um dado de negócio que precise ser espelhado por fora.
- Dias de mês adjacente (antes do dia 1 ou depois do último dia do mês corrente, usados só pra completar a grade de 42 células) aparecem esmaecidos e NUNCA são clicáveis nesta v1 — evita a ambiguidade de 'cliquei num dia e o mês mudou sozinho'. Se surgir um pedido real pra esse atalho (comum em alguns calendários), é decisão nova.
- Grade sempre 6 linhas × 7 colunas fixas (42 células), mesmo em meses que cabem em 5 linhas (a maioria) — evita que a altura do Calendar mude ao trocar de mês, o que seria especialmente ruim dentro de um popover de DatePicker (a posição do popover teria que recalcular a cada navegação).
- Sem grade ARIA completa (role=grid/row/gridcell + navegação por seta tipo planilha) nesta v1 — dias são <button> normais na ordem de Tab, com aria-label descrevendo a data por extenso pra compensar a falta da navegação por seta. Mesma classe de simplificação já usada em Accordion (sem roving tabindex) e Stepper (só horizontal): o padrão ARIA Grid completo fica pra quando um caso de uso real (uso pesado por teclado) pedir.
- aria-current="date" pro dia de hoje — token correto da spec ARIA especificamente pra 'data atual' num calendário, seguindo a mesma disciplina já usada em aria-current="page" (Breadcrumb/NavBar/Link) e aria-current="step" (Stepper): cada contexto usa o valor de aria-current mais específico da spec, nunca um genérico 'true'.
- minDate/maxDate/disabledDate compõem juntos num único estado visual 'disabled' — o dia fica cinza e não-clicável independente de qual das três regras o desabilitou; a distinção do motivo (fora do intervalo vs. bloqueado especificamente) não tem um caso de uso real ainda que justifique estados visuais separados.
- Locale fixo em pt-BR (nomes de mês e dia da semana hardcoded), sem prop de internacionalização — o harness inteiro já é pt-BR (mesmo racional de Alert/Toast/Datatable não terem prop de idioma).
- Dias de mês adjacente usam opacity: 0.5 (valor cru, não é um token de cor) sobre a mesma cor semantic.texto-inativo, em vez de um token de opacidade dedicado — mesma classe de exceção documentada em border-width de Checkbox/Radio/Switch e no padding 0 do Datatable condensed: resolve uma necessidade visual real (esmaecer sem inventar uma nova cor) sem token formal ainda existente pra 'opacidade' no harness.

- CORRIGIDO — BUG REAL encontrado testando no navegador (2026-09-02): .card não declarava font-family/color nenhum — children livre caía pra fonte padrão do navegador (serif) sempre que o Card não estivesse aninhado, por acidente, dentro de algo que já resolvesse a fonte (ex.: .canvas da DS Playground). Pesquisei o padrão usual antes de definir os valores (Tailwind/Material/Ant convergem em progressão não-linear: os primeiros níveis mudam pouco, o salto pro nível mais alto é mais perceptível) — segui essa referência em vez de inventar uma escala do zero.
- low/medium (sombra-pp/sombra-p) são deliberadamente próximos (quase imperceptíveis entre si) — mesmo comportamento da maioria dos sistemas pesquisados, onde os níveis baixos existem mais pra 'descolar sutilmente' a superfície do fundo do que pra criar hierarquia visual forte. high (sombra-m) é o único salto realmente perceptível, pensado pra destacar um Card específico (ex.: hover, seleção) sem chegar no peso visual de um Modal/overlay — que ficaria fora de escopo deste contrato (Card não é feito pra flutuar sobre a página).

Documentado explicitamente como uma dívida a reconciliar com o Figma quando o design formalizar essa coleção — mesmo padrão já usado com fundo-apoio-3/raio-p/texto-g-forte antes.
- Histórico preservado (decisão original, agora superada) — antes desta mudança, Card não tinha sombra porque nenhum token existia e o resto do harness (Button, TextField, Tooltip) usa só borda. Isso deixou de ser um bloqueio: a ausência de token foi resolvida, não a preferência por bordas — 'none' continua sendo o padrão (opt-in, não forçado), então nenhum Card existente é afetado.
- BUG REAL encontrado em teste no navegador — --sombra-pp não estava sendo aplicado (elevation='low' renderizava sem sombra nenhuma), enquanto sombra-p e sombra-m funcionavam normalmente. Causa: o comentário CSS logo acima da declaração continha o trecho 'raio-*/espaco-*' — o '*/' ali fechou o comentário /* ... */ prematuramente, e o texto seguinte do comentário (mais o '*/' real, agora órfão) virou CSS inválido que o parser descartou junto com a declaração de --sombra-pp logo abaixo. Confirmado via inspeção do CSSOM (document.styleSheets), que mostrou só --sombra-p e --sombra-m realmente registrados. Corrigido reescrevendo o comentário sem a sequência '*/' embutida (trocado por 'xp, pp, p, m, g, gg' com vírgulas em vez de barras). Revalidado depois: os 3 níveis resolvem corretamente.
- Contêiner genérico, sem slots fixos de título/corpo/rodapé: decisão explícita do usuário. O único caso de uso real hoje (LoginScreen) já tem título e botões como filhos livres, com estilo próprio — um slot de 'title' do Card provavelmente não bateria com esse estilo sem props extras especulativas. ### Checkbox

- REVISADO — hideLabel adicionado depois que datatable.contract.json precisou de um checkbox sem texto visível ao lado (coluna de seleção de linha/'selecionar todos', célula estreita). A primeira versão deste contrato resolvia isso proibindo Checkbox sem label visível, o que levou o Datatable a usar um <input> nativo por fora do átomo — quebrando a regra maior do harness de nunca ter interatividade fora de um componente. hideLabel resolve as duas coisas: o rótulo continua no DOM (nome acessível real, não um aria-label solto que fica dessincronizado do texto visível), só troca de visível pra clip/1px (mesma técnica sr-only que este componente já usa no próprio <input>, ver .input em Checkbox.module.css) quando true. Datatable agora usa <Checkbox hideLabel label="Selecionar linha X" .../> em vez de reimplementar a caixa.
- Não depende de FieldLabel: a tipografia de FieldLabel (texto-rotulo-campo, peso 500) foi desenhada pra um rótulo ACIMA de um campo, não pro texto ao lado de um controle pequeno — usar aqui produziria peso visual errado. Além disso, o padrão de clique é diferente: em Checkbox, o <label> INTEIRO (caixa + texto) é clicável por decisão (maior alvo de toque, bom pro público 60+); em FieldLabel, o gatilho de ícone é deliberadamente mantido FORA do <label> pra não disparar o campo por engano — situação que não existe aqui. Checkbox implementa seu próprio <label> simples.
- Alvo de toque 44×44px (herda a decisão já registrada em button.contract.json/text-field.contract.json para o público 60+), com a caixa visual em structural.icone-medio (20px) centralizada dentro — a área clicável real é a linha inteira via <label>, não só a caixa.
- RESOLVIDO — HelperText fica alinhado com o texto do rótulo, não com a borda esquerda da linha (que ficaria embaixo da caixa). Recuo de calc(icone-medio + espaco-pp) — os mesmos dois tokens que já definem a largura da caixa e o gap entre caixa e texto, não um valor novo inventado.
- raio-xp (4px) pra caixa — reaproveita token estrutural existente; não é raio-pp (8px, usado em Button/TextField) porque a caixa é bem menor, um raio proporcionalmente menor lê melhor num controle de 20px.
- Borda da caixa fixa em 2px — não é token (mesmo tipo de constante não-tokenizada já usada no traço do Spinner).
- Cor de check reaproveita semantic.acao-primaria (fundo) + semantic.acao-primaria-texto (glifo do check, branco) — os mesmos tokens que o Button variant=primary já usa, não uma família nova de 'seleção'.
- RESOLVIDO — state=disabled + checked/indeterminate: o glifo (check/traço) troca de semantic.acao-primaria-texto (branco) para semantic.icone-inativo. Bug real relatado: branco sobre o fundo cinza-claro de acao-inativa ficava quase invisível. icone-inativo tem o mesmo valor de semantic.borda-inativo (a borda da caixa desabilitada), então o glifo passa a combinar com a borda em vez de tentar simular o contraste do estado habilitado.
- Checkbox depende de HelperText porque uso isolado (ex.: 'aceitar termos') comumente precisa de mensagem de erro própria. Radio não tem essa dependência — ver decisions em radio.contract.json.
- indeterminate é propriedade DOM (element.indeterminate), não atributo HTML — implementação precisa de useRef + useEffect pra sincronizar, não dá pra resolver só com props declarativas do <input>.
- Erro + foco: erro vence visualmente, mesma regra já fixada em text-field.contract.json — aplicada aqui por consistência entre os contratos de data-entry, não é uma nova decisão reaberta.
- AJUSTADO a pedido do usuário — fundo do campo trocado de semantic.fundo-superficie pra semantic.fundo-campo (token novo): 'o fundo dos inputs de forma geral, devem ser levemente mais escuros que a cor de fundo da página onde estão, para destacar melhor'. No modo claro fundo-campo é idêntico a fundo-superficie (sem mudança visual, branco com borda já bastava) — só no modo escuro os dois valores divergem (fundo-campo um degrau mais escuro que a página), porque era só ali que o campo ficava indistinguível da própria página por trás.

### Chip

- RESOLVIDO com o usuário — Chip suporta os dois comportamentos, independentes: selected/onToggle (modo filtro/toggle) e removable/onRemove (modo tag). Um chip pode ter só um dos dois, os dois juntos, ou nenhum (aí é só um rótulo estático, sem interação — mas nesse caso Badge provavelmente já resolve melhor, ver whenNotToUse).
- RESOLVIDO com o usuário — Chip TEM variantes de cor por status (info/success/warning/error), mesmos tokens sólidos do Badge, além de neutral.
- Estado selected usa um visual FIXO (acao-primaria + acao-primaria-texto, os mesmos tokens do Button variant=primary), independente da variant — decisão do agente, não perguntada de novo pra não aumentar a interferência: seleção é uma dimensão diferente de status. Um chip 'error' selecionado não vira 'mais vermelho', vira 'azul/verde de seleção' como qualquer outro chip selecionado — o mesmo padrão visual de 'isto está ativo' em todo lugar do produto, independente de qual filtro é. Se um caso real pedir seleção com cor por variant, é decisão nova.
- Solução pro problema de HTML inválido (<button> dentro de <button>, quando um chip é selecionável E removível ao mesmo tempo): o wrapper é um <span> não-interativo; o label vira <button aria-pressed> SÓ quando selected é usado; o botão de remover é sempre um <button> IRMÃO, nunca aninhado. Isso preserva navegação por Tab independente pros dois controles, sem quebrar HTML nem reimplementar semântica de botão.
- Sem leading icon/avatar (ex.: chip com foto pequena de um usuário) neste contrato — não foi pedido, e adicionar agora seria especular; candidato natural se surgir um caso real (ex.: chip de 'responsável' com Avatar).

Documentado explicitamente em vez de simplesmente ignorar a régua de toque do resto do harness.

### ComboBox

- CORRIGIDO — auditoria de contratos (2026-09-01): raio-xp adicionado a radius, mesmo gap do select.contract.json (botão-gatilho e ícone de limpar usam raio-xp, só o popup usava raio-pp, já declarado).

- Estado interno de 'busca' (query) é separado do value controlado: o <input> mostra o texto digitado enquanto o popup está aberto, mas volta a mostrar o label selecionado (single) ou o resumo truncado (multiple) assim que fecha — sem confirmação explícita (Enter ou clique numa opção), a busca digitada nunca vira o value.
- Ao abrir (foco no campo), limpa pra busca vazia (mostra todas as opções) em vez de manter o label atual como texto pra editar — modelo mental mais simples ('abrir = nova busca'), consistente com implementações de referência (ex.: seletor de labels do GitHub). A opção já selecionada continua visível com um ícone de check dentro da lista.

- Sem useTypeahead do floating-ui aqui (diferente do Select): a própria digitação já filtra a lista em tempo real, um buffer de typeahead paralelo seria redundante e brigaria pela mesma tecla.

- Foco real de teclado nunca sai do <input> (navegação 'virtual', mesma técnica do Select, mesmos cuidados de foco já resolvidos lá — onMouseDown+preventDefault nas opções, id real em cada option pra aria-activedescendant funcionar).
- Erro + foco: erro vence visualmente — mesma regra já fixada em text-field.contract.json/select.contract.json, aplicada por consistência entre contratos de data-entry.
- AJUSTADO a pedido do usuário — fundo do campo trocado de semantic.fundo-superficie pra semantic.fundo-campo (token novo): 'o fundo dos inputs de forma geral, devem ser levemente mais escuros que a cor de fundo da página onde estão, para destacar melhor'. ### CommentComposer

- Nasceu da análise de sistemas legados (analise-sistemas-legados.md, item 1.8) — painel de 'Notas & Observações' de uma tela de videochamada/atendimento: textarea + ícones utilitários (anexar imagem, marcar importante, emoji) + botão Publicar desabilitado até haver texto.

- Botão Publicar é sempre variant='primary' (não exposto como prop) — diferente do ActionCard (que expõe primaryVariant porque os prints legados mostravam cores variadas), aqui o print legado mostrava sempre o mesmo botão sólido de ação principal; não há padrão real pedindo variação de cor pra esse botão específico.
- AJUSTADO a pedido do usuário — novo trio de props maxLength/showCharacterCount/limitMode, pra 'adicionar ou remover o contador de caracteres... e também a possibilidade de limitar o campo, com mensagem de alerta quando chegar ao limite (bloqueando a digitação ou permitido digitar e alertando e bloqueando o botão)'. maxLength/showCharacterCount são só repasse direto pro Textarea interno (ver textarea.contract.json, que ganhou essas props na mesma leva de mudanças) — CommentComposer não duplica a lógica do contador, só expõe as mesmas props um nível acima. limitMode é a peça nova específica do CommentComposer (Textarea sozinho não tem noção de 'botão de publicar' pra bloquear): 'block' passa enforceMaxLength=true pro Textarea (bloqueio nativo, replica o comportamento já existente antes deste ajuste); 'warn' passa enforceMaxLength=false (digitação livre) e adiciona a lógica de calcular overLimit = value.length > maxLength, que vira: (1) state='error' + helperText de aviso no Textarea, (2) canSubmit=false até o texto voltar a caber.

### ConfirmDialog

- ConfirmDialog NÃO fecha sozinho depois de onConfirm — mesmo padrão já usado no Modal de confirmação da Datatable (setConfirmation(null) só acontece depois que a ação de verdade termina). Isso evita fechar o dialog e já esconder o Modal antes de uma chamada assíncrona (ex.: excluir via API) confirmar sucesso — quem consome controla open e decide fechar no momento certo (sucesso, erro, ou imediatamente se a ação for síncrona).
- confirmVariant só tem 'primary'/'destructive' (não todas as variants do Button) — uma confirmação é sempre 'a ação principal que vai acontecer' (primary) ou 'uma ação que remove/destrói algo' (destructive); as outras variants do Button (secondary, subtle, link) não fazem sentido semântico pra um botão de confirmação final.
- confirmState='loading' desabilita TAMBÉM o Cancelar, não só trava o Confirmar — evita fechar o dialog no meio de uma ação já em andamento (ex.: cancelar visualmente enquanto a exclusão já está sendo processada no servidor), mesmo racional de não deixar o usuário 'perder o rastro' de uma ação que já começou.
- Foco inicial nunca vai pro botão de confirmação — decisão de segurança consolidada em confirmações destrutivas de mercado (um Enter reflexo logo após abrir o dialog não deveria disparar a ação); o Modal por baixo já cuida do foco preso, ConfirmDialog só garante que o alvo inicial não é o botão perigoso.
- Reaproveita Modal (size='small') e Button diretamente, sem declarar overlay/borda/sombra próprios — ConfirmDialog é uma composição específica de dois átomos/organismos já existentes e testados, não uma superfície nova.

### CopyButton

- Estado 'copied' é transiente e interno (~2s, via setTimeout), não uma prop controlada — mesma classe de decisão já usada pra outros estados de UI efêmeros do harness (ex.: editingRowKey do Datatable, popovers abertos): é feedback local de uma ação que já aconteceu, não um dado que precise ser espelhado por fora.
- aria-label muda pra confirmar a cópia (em vez de depender só de uma mudança visual de ícone) — decisão de acessibilidade: quem usa leitor de tela precisa saber que a cópia funcionou sem precisar 'ver' o ícone virar um check.
- navigator.clipboard.writeText falhando (permissão negada, contexto não-seguro, API ausente) é capturado e silenciosamente NÃO entra no estado 'copied' — sem lançar exceção, sem quebrar a página. Não foi adicionado um estado de erro visual nesta v1 (ex.: 'Falha ao copiar') porque esse caso é raro o bastante (a maioria dos navegadores modernos suporta em contexto HTTPS) pra não justificar mais um estado só pra ele agora; se aparecer um caso real, é decisão nova.
- Sempre iconOnly, nunca com label de texto visível — CopyButton é pensado pra ficar ao lado de outro conteúdo (o texto que está sendo copiado já está visível em outro lugar), um botão com texto próprio ('Copiar') competiria visualmente com esse conteúdo principal.

### DataField

- Nasceu da análise de sistemas legados (analise-sistemas-legados.md, item 1.1) — padrão mais repetido de todos os prints analisados (Visão 360, Credenciamento, Internações, proposta do corretor), sempre remontado na mão porque o harness não tinha um átomo dedicado pra 'campo somente-leitura rotulado'.
- NÃO é o mesmo componente que StackedText, apesar da semelhança superficial ('duas linhas de texto'): StackedText é texto principal EM CIMA + secundário EMBAIXO, mesma hierarquia visual (os dois são 'texto simples', usado solto dentro de células de tabela, sem borda/caixa, sem ícone). DataField inverte a hierarquia (rótulo pequeno em cima, valor grande embaixo), sempre dentro de uma caixa com borda, e aceita ícone prefixando o valor — são dois padrões visuais e semânticos diferentes (identidade compacta em tabela vs. campo rotulado em painel de detalhe), por isso ganharam contratos separados em vez de um prop a mais em StackedText.
- Ícone prefixa a linha de VALOR, não o rótulo — reflete o padrão observado nos prints reais (ex.: ícone de usuário ao lado do nome, não ao lado da palavra 'Nome completo').
- value é sempre string (não ReactNode livre) nesta v1 — mantém o contrato simples e prevê exatamente o caso observado (texto formatado). Se surgir um caso real de valor rico (ex.: um Chip ou Badge dentro do valor), é decisão nova, não antecipada aqui.
- Estritamente só-leitura nesta v1, sem um modo 'editável' — a análise já cogitava essa possibilidade, mas nenhum caso real observado nos prints mostrava esse campo específico virando editável in-place; construir esse modo agora seria especular. Quando um campo precisa ser editável, o padrão do harness já é trocar pra TextField/Select (ex.: já acontece hoje na edição de linha do Datatable).
- Caixa com borda (não só texto solto) — reflete fielmente o padrão visual mais comum nos prints (rótulo+valor sempre dentro de uma caixa com borda leve), diferente de simplesmente empilhar dois textos sem contêiner.
- Rótulo em type-style.texto-p (14px/400, texto-secundario) e valor em type-style.texto-m (16px/400, texto-primario) — cria a hierarquia de tamanho vista nos prints (rótulo visivelmente menor que o valor) reaproveitando os dois estilos de tipografia já existentes no harness, sem introduzir um terceiro.
- BUG REAL corrigido em teste no navegador — a caixa tinha `gap: espaco-xp` (4px) explícito entre rótulo e valor, além do `padding: espaco-pp` (8px) da caixa. Mesmo o gap explícito sendo numericamente menor que o padding, o line-height de cada estilo tipográfico (texto-p 1.4, texto-m 1.5) adiciona espaçamento extra (leading) acima/abaixo de cada linha de texto, que se soma ao gap explícito — o resultado visual era um espaço entre rótulo e valor maior que o espaço entre o texto e a borda da caixa, mesmo com os tokens 'certos' aplicados. Corrigido removendo o gap explícito (`gap: 0`) e deixando o line-height de cada linha ser a única fonte de espaçamento entre elas — o padding da caixa (uniforme nos 4 lados) passa a dominar visualmente a régua de espaçamento, como esperado. Reforça uma lição geral do harness: gap explícito + line-height não são aditivamente intuitivos, então composições de texto empilhado devem ser conferidas visualmente no navegador, não só pelos valores nominais dos tokens.
- BUG REAL corrigido em teste no navegador (2ª rodada, mesma causa raiz da anterior) — mesmo com padding numericamente igual nos 4 lados (`padding: espaco-pp`, 8px), o padding vertical (topo/baixo) lia visualmente maior que o horizontal (esquerda/direita). Causa: o line-height das linhas de texto adiciona leading vertical (acima da primeira linha, abaixo da última) que não tem equivalente horizontal — texto não tem 'leading lateral', só o padding puro. Corrigido trocando pra `padding: espaco-pp espaco-p` (8px vertical / 12px horizontal) — o padding horizontal levemente maior compensa a ausência de leading lateral, equilibrando a percepção visual dos 4 lados. Confirmado no navegador que a caixa passou a ler como 'padding uniforme' de verdade, não só nominalmente.

### Datatable

- CORRIGIDO — auditoria de A11y (2026-09-01): BUG REAL, os menus de coluna visível e exportação (useDropdown interno) usavam floating-ui cru sem FloatingFocusManager — mesmo gap já documentado em popover.contract.json/navbar.contract.json. Corrigido envolvendo os dois painéis em <FloatingFocusManager context={...} modal={false}>, useDropdown agora também expõe context no retorno.
- Um componente só (Datatable), features opt-in por prop/coluna — decisão explícita do usuário em vez de dois componentes separados (Table simples + DataTable avançado). A versão 'simples' é literalmente usar Datatable sem selectable/sort/filtro/paginação/edição ativados.
- sortMode e filterMode existem separados, cada um 'client' | 'server' — decisão explícita do usuário. Em 'client' o Datatable faz o trabalho de ordenar/filtrar sozinho sobre o array data recebido; em 'server' ele só notifica (onSortChange/onFilterChange) e espera receber data já processado de volta. paginationMode segue o mesmo racional para consistência entre os 3 mecanismos.
- Ciclo de ordenação de 3 estados por coluna: nenhum → ascendente → descendente → nenhum. Decisão do agente: permite ao usuário sempre voltar pra ordem original de data sem precisar recarregar a página.
- REVISADO — filtro por coluna agora é OCULTO por padrão (mudança pedida pelo usuário; a v1 tinha o input sempre visível). Dois gatilhos abrem/fecham o MESMO input: clicar no nome da coluna, ou clicar num ícone de funil dedicado ao lado do ícone de ordenação. Quando aberto, o input substitui visualmente o nome da coluna (mesmo espaço). Motivo de ter dois gatilhos em vez de só o funil: pedido explícito do usuário; motivo de o funil existir além do nome: o nome sozinho não é obviamente clicável (sem affordance visual de que abre algo) — o ícone de funil sinaliza a função pra quem não tentar clicar no texto.
- Decisão de resolução de conflito (perguntada ao usuário): quando uma coluna é sortable E filterable ao mesmo tempo, clicar no NOME sempre abre/fecha o filtro, nunca ordena. Ordenar passa a ser EXCLUSIVAMENTE pelo ícone de seta (caret), que agora é um botão separado do nome, não mais o nome inteiro como na v1. Colunas sortable-mas-não-filterable: nome fica estático (não clicável), só o caret ordena. Colunas filterable-mas-não-sortable: nome abre/fecha filtro, sem ícone de caret.
- Filtro é sempre substring case-insensitive normalizado por acento (reaproveita shared/normalizeForSearch.ts, já usado por Select/ComboBox) — não existe filterType configurável nesta versão.
- 'Selecionar todos' no cabeçalho seleciona só as linhas da página atual (quando paginationEnabled=true), não o dataset inteiro — evita o Datatable precisar conhecer todos os rowKey de páginas que talvez nunca tenham sido carregadas em modo server.
- totalRows só é obrigatório em paginationMode='server' — em 'client' o Datatable já tem o array data completo e deriva o total de data.length.
- Troca de pageSize sempre reseta page para 1 — evita ficar numa página que não existe mais depois de aumentar o tamanho da página.
- structural.icone-medio (20px) em tokensAllowed.iconSize — tamanho do átomo Checkbox (definido no próprio checkbox.contract.json, não redefinido aqui). structural.espaco-g — padding generoso da célula de linha vazia (mesma escala usada em Card/Modal).
- RESOLVIDO (era um conflito real documentado na v1) — checkbox.contract.json agora tem uma prop hideLabel (rótulo continua no DOM como nome acessível, só fica visualmente oculto via técnica sr-only) em vez de proibir Checkbox sem rótulo visível. Isso substituiu o <input type="checkbox"> nativo que a v1 usava na coluna de seleção — agora é <Checkbox hideLabel label="Selecionar linha X" .../> de verdade, seguindo a regra de que nenhum controle interativo deste componente pode existir fora de um átomo do harness.
- Seletor de itens por página e input de filtro continuam nativos (<select>/<input>), não usam os átomos Select/TextField — decisão preservada da v1 (peso visual desproporcional: Select é um combobox completo com popup via floating-ui, TextField carrega FieldLabel/HelperText; nenhum dos dois cabe numa célula de cabeçalho ou num controle secundário de paginação). A regra 'nada fora de um componente' pedida pelo usuário nesta revisão foi interpretada como valendo pra CONTROLES COM ESTADO VISUAL PRÓPRIO (como o Checkbox, que tem cor/ícone/borda variando por estado) — inputs de texto simples e o <select> nativo do navegador não têm essa lacuna de estilização (o CSS do harness já os estiliza igual), então continuam nativos. Se o usuário quiser estender a regra literalmente a esses dois também, é uma decisão nova a pedir.
- Edit control tipo 'select' (column.editControl.type='select') usa o átomo Select, não um <select> nativo — diferente do pageSize/filtro, aqui é uma escolha de valor real durante uma ação de edição (mais parecido com um campo de formulário do que com um controle secundário de UI). Select já suporta uso sem label visível (label é required:false no próprio contrato dele), então não precisa de exceção nova.
- Edit control tipo 'text' (column.editControl.type='text') usa um <input> de texto simples, mesmo padrão do input de filtro — não o átomo TextField completo (FieldLabel/HelperText não cabem numa célula de tabela em edição inline, mesmo racional do filtro).
- Estado de 'qual linha está em edição' e os valores temporários dos inputs (draft) ficam INTERNOS ao Datatable, não controlados por props — decisão explícita do usuário (perguntada, ver conversa). Motivo do usuário/agente: edição inline é um estado transiente e local (não precisa sobreviver a um refresh nem ser mockado em outro lugar), diferente de sort/filtro/seleção que fazem sentido restaurar/compartilhar externamente. Datatable expõe só onRowSave(rowKey, values, row), chamado depois da confirmação.
- Coluna de ações não é um conceito especial — continua sendo column.render comum. O que mudou: render agora recebe um 3º argumento, helpers (DatatableRowHelpers: isEditing, isDisabled, startEdit, cancelEdit, requestSave, requestToggleDisabled), pra qualquer coluna (normalmente só a de ações usa) disparar edição/salvar/cancelar/habilitar-desabilitar daquela linha específica. Evita introduzir um prop 'actions' paralelo (proibido desde a v1) mesmo com a feature de edição/habilitar crescendo.
- RESOLVIDO — bug real encontrado testando no navegador: a primeira versão do exemplo completo usava column.accessor pra formatar o Status ('Pago' em vez de 'pago') e reaproveitava esse valor formatado tanto pra exibição/filtro quanto pra seedar o draft de edição — o Select de edição abria vazio porque 'Pago' não batia com nenhum editControl.options[].value ('pago'). Regra fixada: em colunas editable=true, accessor sempre retorna o valor BRUTO (o mesmo que bate com editControl.options), e é render (que recebe esse valor bruto como 1º argumento) quem formata pra exibição — não accessor. Corrigido no exemplo removendo o accessor da coluna Status e formatando dentro de render.
- Apenas colunas com editable=true viram input quando a linha entra em modo de edição — não 'todas as colunas' ao pé da letra do pedido original. Colunas computadas (ex.: 'Ações', valores derivados via accessor/render que não mapeiam 1:1 pra um campo editável) não têm como virar um input genérico sem um editControl declarado; forçar isso quebraria colunas com render customizado. Decisão do agente, documentada por não ter sido perguntada.
- requestSave() SEMPRE abre um Modal de confirmação interno (reaproveita o átomo Modal) antes de chamar onRowSave — pedido explícito do usuário. cancelEdit() NÃO abre modal — descarta o draft e sai do modo de edição imediatamente, porque nada foi persistido ainda (não há risco de perda de dado salvo, só de um formulário preenchido, mesmo racional de Esc não-destrutivo usado em outros contratos).

### DatePicker

- Modo range é resolvido como DOIS gatilhos/popovers independentes (Início/Fim), cada um com seu próprio Calendar de data única — não uma única grade com duas datas destacadas simultaneamente. Motivo prático: Calendar (ver calendar.contract.json, decisions) documentou explicitamente que ainda não suporta destacar um intervalo dentro da própria grade; construir isso agora seria antecipar uma necessidade sem um caso de uso real que dependa da grade única. A restrição de 'fim não pode ser antes de início' é aplicada de fora, setando minDate do segundo Calendar como value.start.
- value/onChange mudam de formato conforme range (string|null vs {start,end}), mesmo padrão de discriminated union já usado em Select (multiple: false=string, true=string[]) — o tipo muda com uma prop booleana em vez de dois componentes/nomes diferentes.
- Gatilho reaproveita exatamente o estilo visual do trigger de Select (mesma altura, borda, radius, tipografia) — o usuário já reconhece esse padrão como 'campo com popover' no harness, não faz sentido inventar uma segunda aparência pro mesmo conceito de interação.
- Selecionar uma data fecha o popover automaticamente (modo único) — mesma escolha já feita em Select de fechar ao confirmar uma opção única (mantém aberto só no caso multiple, que não existe aqui).
- Formato de exibição fixo em DD/MM/AAAA (nunca o ISO cru) — value interno continua ISO (mesmo formato do Calendar, fácil de comparar/ordenar como string), só a apresentação ao usuário é convertida.
- AJUSTADO a pedido do usuário — campo passou de <button> (só seleção via Calendar) pra <input type='text'> com máscara automática: usuário digita só dígitos (0-9), a máscara insere as barras '/' sozinha nas posições certas (DD/MM/AAAA), sem depender de o usuário digitar separador nenhum. Resolve a ambiguidade de formato livre (ex.: '03/04/26' vs '3-4-2026') que motivava a decisão anterior de não permitir digitação — a máscara elimina a ambiguidade ao fixar a ordem e o formato de antemão, o usuário só entra com números.
- Validação/parsing só considera a data completa (8 dígitos): dia dentro do intervalo do mês (considerando ano bissexto via Date nativo), mês 1-12. Data incompleta ou inválida nunca dispara onChange — o campo mostra a máscara parcial digitada até então, mas value só muda quando os 8 dígitos formam uma data real dentro de minDate/maxDate/disabledDate.
- Ao perder o foco (blur) com uma data incompleta/inválida/fora do intervalo permitido, o campo reverte pro texto do último value confirmado (ou vazio, se nunca houve um) — nunca deixa um texto parcial ou inválido visível depois que o usuário sai do campo.
- useFocus adicionado ao floating-ui (além de useClick) — abrir o popover também ao focar o campo via Tab, não só ao clicar; contribui pra digitação e seleção pelo Calendar se sentirem como o mesmo campo, não dois modos desconectados.
- Selecionar uma data no Calendar continua preenchendo o campo de texto (via useEffect sincronizando o texto exibido com o value externo) — os dois caminhos (digitar ou clicar no Calendar) sempre convergem pro mesmo estado visual.
- BUG REAL corrigido em teste no navegador — onChange/onBlur do input eram passados como props JSX soltas ANTES do spread de getReferenceProps() do floating-ui, que por sua vez também define onChange/onBlur próprios; o spread posterior SOBRESCREVIA silenciosamente os handlers customizados em vez de compor os dois (nenhum erro, a máscara funcionava mas a reversão em blur pra um valor inválido nunca disparava — um texto de data quebrada tipo '32/13/2026' ficava visível permanentemente). Corrigido passando onChange/onBlur como argumento de getReferenceProps({ onChange, onBlur }), que é a forma correta de compor handlers customizados com os internos do floating-ui — confirmado no navegador que digitar uma data inválida e sair do campo agora reverte pro último value confirmado.
- AJUSTADO a pedido do usuário — nova prop 'showPicker' (default true). Implementada desabilitando os hooks useClick/useFocus/useDismiss do floating-ui via { enabled: showPicker } em vez de simplesmente não renderizar o popover — assim o campo nunca entra em estado 'open' quando showPicker=false (não é só uma questão visual, o popover realmente nunca monta). O ícone caret-down decorativo também some nesse modo (não faz sentido mostrar um indicador de 'isso abre algo' quando nada abre) e aria-haspopup/aria-expanded ficam undefined em vez de false, porque semanticamente o campo deixou de ser um combobox com popup. Digitação com máscara continua funcionando normalmente nos dois modos — showPicker só controla a existência do popover, nunca a validação/máscara do texto.
- AJUSTADO a pedido do usuário — popover do Calendar ganhou box-shadow (structural.sombra-p, mesmo token já usado no Popover genérico) além da borda que já existia, pra ter elevação visual consistente com o resto dos popovers do harness em vez de parecer 'colado' no fundo da página.
- AJUSTADO a pedido do usuário (uso no DashboardTemplate, item 5.3) — dois reforços: (1) Icon 'calendar' fixo à esquerda do trigger, sempre presente (não configurável, diferente do leftIcon opcional do TextField) — todo DatePicker se beneficia dessa pista visual universal de 'isso é um campo de data', não é um caso específico de um consumidor só; (2) nova prop hideLabel pra permitir omitir o FieldLabel visível (ex.: 'Início'/'Fim' de um range dentro de uma FilterBar, onde os rótulos já eram redundantes) SEM perder o nome acessível — o texto do label continua sendo aplicado como aria-label no input quando hideLabel=true, escape explícito documentado em forbidden pra nunca deixar o campo sem nome acessível.
- REVISADO a pedido do usuário — a decisão acima ('Icon calendar sempre presente, não configurável') foi revertida: nova prop showIcon (default true, preserva o comportamento visual de antes pra quem já usa o componente) permite esconder o ícone. Motivo: mesmo pedido feito de uma vez pros três pickers de data/hora do harness (DatePicker/TimePicker/DateTimePicker) — não é mais tratado como 'pista visual universal inegociável', vira uma preferência de densidade visual do consumidor.
- AJUSTADO a pedido do usuário — fundo do campo trocado de semantic.fundo-superficie pra semantic.fundo-campo (token novo): 'o fundo dos inputs de forma geral, devem ser levemente mais escuros que a cor de fundo da página onde estão, para destacar melhor'. No modo claro fundo-campo é idêntico a fundo-superficie (sem mudança visual, branco com borda já bastava) — só no modo escuro os dois valores divergem (fundo-campo um degrau mais escuro que a página), porque era só ali que o campo ficava indistinguível da própria página por trás.

### DateTimePicker

- CORRIGIDO — auditoria de contratos (2026-09-01): texto-secundario adicionado a text — usado no componente (provavelmente rótulo/legenda auxiliar) mas ausente da whitelist.

### Divider

- RESOLVIDO com o usuário — suporta horizontal E vertical desde já (diferente do padrão 'espera um caso de uso real' aplicado a Radio/RadioGroup): o prop orientation já cobre os dois eixos porque a implementação de ambos é simétrica (só troca qual dimensão é 1px vs 100%), não há custo real de manter os dois versus só um.
- RESOLVIDO com o usuário — suporta label opcional centralizado (ex.: 'ou' entre botões de login social). label só é válido com orientation='horizontal' — combinar com vertical fica proibido neste contrato até surgir um caso real que justifique o tratamento visual de texto num traço vertical estreito.
- Espessura da linha fixa em 1px — não é token (tokens.json não tem uma coleção de espessura de borda genérica, só foco-espessura, que é especificamente pro anel de foco). Mesma disciplina de 'constante não-tokenizada' já usada na borda de 2px do Checkbox/Radio e no traço do Spinner — 1px aqui porque Divider é uma linha estrutural fina (hairline), não um controle de formulário que precisa de peso visual maior.
- Cor da linha reaproveita semantic.borda-base, o mesmo token neutro já usado como borda padrão em Checkbox/Radio/Switch/TextField — não cria uma família de cor 'divisor' separada.
- Cor do label usa semantic.texto-secundario (tom mais discreto que texto-primario) — o rótulo de um divisor é auxiliar/contextual, não o conteúdo principal da tela, mesmo raciocínio de contraste reduzido já usado em HelperText (texto-secundario) vs texto de campo (texto-primario).
- Tipografia do label usa type-style.texto-p (14px), menor que texto-m (16px usado em Checkbox/Radio/Switch) — um rótulo de divisor é deliberadamente mais discreto que o texto de um controle interativo.
- Sem states além de 'static' — Divider é puramente estrutural/visual, sem interação, mesmo padrão já usado em Card.
- Vertical exige altura do contexto (container pai com altura definida ou flex align-items:stretch) — Divider não fixa uma altura própria em pixels porque não tem como saber a altura correta do conteúdo que está separando; é responsabilidade de layout do consumidor, não do componente.
- role=separator com aria-orientation explícito nos dois casos (não só quando vertical, que é quando teria efeito real no default do role) — decisão de sempre declarar explicitamente em vez de confiar no valor implícito do navegador, mesma filosofia de 'não deixar implícito o que pode ser explícito' já usada em outros contratos (ex.: aria-invalid explícito em vez de inferido do estilo).

- PERGUNTADO AO USUÁRIO — layout='push' é uma prop NOVA (opt-in), não uma mudança de comportamento do modal=false existente. Mesmo padrão 'estado local otimista + callback pra fonte de verdade' usado em qualquer lista arrastável real (ex.: exemplo oficial multi-container do próprio dnd-kit).
- PointerSensor com activationConstraint.distance=8 — um clique simples (sem arrastar 8px) nunca inicia um drag, garantindo que o botão de overflow (···) dentro do card continue 100% clicável mesmo com o card inteiro funcionando como alça de arrasto (área de drag = card inteiro, não uma alcinha separada — mais fácil de pegar, print legado não mostrava uma alça dedicada).
- Card sendo arrastado usa DragOverlay do dnd-kit (uma cópia visual solta do fluxo normal, seguindo o ponteiro) — o card original na lista fica com opacity:0.4 enquanto arrasta, prática padrão do dnd-kit pra deixar claro qual item está em movimento sem duplicar visualmente.
- LIMITAÇÃO CONHECIDA — só PointerSensor (mouse/touch/caneta), sem KeyboardSensor: reordenar via teclado não funciona nesta v1 (ver a11y, keyboard). Adicionar suporte a teclado é incremental quando um caso real pedir.
- AJUSTADO a pedido do usuário — colunas agora esticam pra MESMA altura (`.board` trocou `align-items:flex-start` por `align-items:stretch`) e cada coluna tem scroll vertical PRÓPRIO no corpo (`.columnBody` com `flex:1; min-height:0; overflow-y:auto`), com o cabeçalho (título+contador) fixo fora da área de scroll (`flex-shrink:0`). Isso faz o board precisar de uma altura definida vinda de fora (de quem consome) — decisão explícita: KanbanBoard não assume mais 'altura pelo conteúdo', ele PREENCHE o espaço vertical disponível do container pai. Quem consome (ex.: KanbanTemplate) é responsável por dar esse espaço uma altura real (100dvh menos header, por exemplo).
- columns não é um enum fixo do harness (diferente de priority no TicketCard) — o vocabulário de estágios (Novos/Em andamento/Concluídos vs. outros nomes) é decisão de cada domínio que consome o board, não do design system. O harness só define COMO uma coluna se parece (cabeçalho com contador + lista de cards), não QUAIS colunas existem.
- Callbacks de ação (onDuplicate/onToggleEnabled/onEdit/onViewDetails/onDelete) recebem ticketId em vez de exigir que o consumidor monte 5 callbacks fechados por ticket manualmente — KanbanBoard já faz esse fechamento (closure) internamente ao passar pra cada TicketCard, poupando repetição óbvia de quem consome um board inteiro (diferente de reimplementar toda a lógica de menu, que continua 100% dentro do TicketCard).
- Contador do cabeçalho reaproveita Badge (variant='neutral', count=tickets.length) — nenhum componente/token novo criado só pra esse número.
- Coluna vazia mostra um texto simples ('Nenhum ticket'), não o componente EmptyState — EmptyState foi desenhado pra ocupar uma área de destaque (ícone extraLarge + título + ação), pesado demais pra uma coluna estreita de 280px; aqui é só um texto de apoio (texto-inativo), mesmo racional de peso visual proporcional ao espaço disponível já aplicado em outros contratos.
- Board tem scroll horizontal nativo (overflow-x: auto) com colunas de largura fixa (280px) — mesmo padrão visual de um Kanban tradicional, sem quebrar colunas em várias linhas.
- BUG REAL corrigido em teste no navegador — .board (flex item dentro do wrapper de demo, também flex) não tinha width:100%/min-width:0, então o próprio flex item crescia até a largura do conteúdo (soma das colunas) em vez de respeitar o espaço do pai; o overflow-x:auto declarado nunca engatava (scrollWidth==clientWidth do próprio board) e quem escondia o excesso era o ancestral mais acima, cortando a primeira coluna e centralizando o corte dos dois lados. Mesma classe de bug já documentada no ProgressList (item 3.1 do roadmap) — root de um componente que precisa preencher o container sempre precisa de width:100% explícito quando vive dentro de flex; aqui, adicionalmente, min-width:0 pra permitir que o próprio flex item ENCOLHA abaixo do min-content e ative seu scroll interno, em vez de só crescer.

### Link

- Sem tipografia própria (nenhum type-style em tokensAllowed): diferente de todo o resto do harness, Link usa font: inherit — ele tipicamente vive dentro de um parágrafo, item de navegação ou rodapé com tamanho/família já definidos pelo contexto, e forçar um type-style fixo faria ele destoar do texto ao redor. Só a cor (acao-link-texto) é fixa.
- external=true controla tudo relacionado a abrir em nova aba de uma vez (target, rel, ícone, texto oculto) — não existe uma prop 'target' separada porque target='_blank' sem rel='noopener noreferrer' é uma falha de segurança real (a página aberta ganha acesso a window.opener), não uma escolha estética; expor as duas props separadas criaria a possibilidade de esquecer o rel.
- external sobrepõe rightIcon manual, mesma regra de precedência já usada no TextField (type=password sobrepõe rightIcon) — não dá pra combinar um rightIcon customizado com o indicador de link externo no mesmo lado.
- disabled remove o atributo href em vez de usar aria-disabled sozinho: <a> não tem atributo disabled nativo, e sem href o elemento já não é focável nem clicável nativamente — mesmo efeito prático do Button disabled (sai da tabulação), só que pela ausência do atributo que o torna interativo, não por um atributo de bloqueio.
- Ícone de 'abre em nova aba' fica decorative=true (só visual) — o anúncio real pro leitor de tela é um texto visualmente oculto '(abre em nova aba)' concatenado ao label, não um accessibleLabel no ícone (evita duplicar o anúncio).
- onPress é efeito colateral opcional, nunca o mecanismo de navegação em si (diferente do Button) — a navegação real acontece via href nativo, então Link continua funcionando sem JavaScript.
- underline é boolean, não um variant novo (ex.: 'default'/'underline') — só duas combinações existem hoje e ambas usam exatamente os mesmos tokens de cor, só o text-decoration muda. Mesmo padrão já usado no outlined do Button (boolean) em vez de dobrar o enum de variantes.
- REVISADO — prop current adicionada: lacuna real encontrada implementando navbar.contract.json (item ativo de uma barra de navegação precisa de aria-current=page + destaque visual, e Link não tinha como expressar isso). current=true reaproveita acao-link-texto-sobreposto (a mesma cor que já era usada no :hover) como cor de REPOUSO — não introduz token novo, só aplica um tom que já existia no contrato pra um estado que também já existia (hover), agora também disponível como estado 'ativo' persistente. Diferente da decisão do último item do Breadcrumb (que vira texto estático, não-clicável): aqui o item current continua sendo um <a href> real e clicável, porque em NavBar clicar no item já ativo é uma ação válida (ex.: recarregar/voltar ao topo da área atual).

Modal não inventa um botão de cancelar sozinho porque não sabe qual é a ação certa (voltar? descartar? um terceiro estado?) — isso é decisão de quem consome, mesmo espírito de Card não ter opinião sobre o conteúdo.

Motivo adicional aqui: forçar um layout fixo de 'botão à direita, botão à esquerda' não bate com todo caso real (ex.: um Modal de formulário pode ter só um botão, ou um link de ajuda ao lado dos botões) — quem consome já tem Button/layout próprios pra montar isso.
- RESOLVIDO com o usuário — cabeçalho SEM linha divisória (border-bottom) separando do corpo; cabeçalho e corpo formam uma superfície visualmente contínua, uma única área com uma padding só ao redor de tudo (ver decisão de padding abaixo), não duas regiões com estilos próprios.
- RESOLVIDO com o usuário — padding segue a MESMA escala e os MESMOS tokens do Card (small=espaco-p, medium=espaco-g, large=espaco-gg, default 'large' igual ao Card), aplicada como UMA padding só ao redor do conjunto cabeçalho+corpo (implementado como um wrapper interno único com essa padding, não duas paddings independentes em header/body) — consistente com o pedido de 'funcionar na mesma lógica dos Cards'.
- RESOLVIDO com o usuário — cabeçalho tem 4 variações possíveis, resultado direto de cruzar title (agora opcional) com dismissible (já existia): título+X (title definido, dismissible=true), só título (title definido, dismissible=false), só X (title omitido, dismissible=true), ou nenhum cabeçalho (title omitido, dismissible=false — corpo começa direto no topo da padding). Não são 4 valores de um enum novo — emergem da combinação das duas props já existentes, sem inflar a API com uma prop 'headerVariant' redundante.
- title deixou de ser obrigatório; quando omitido, accessibleLabel assume o papel de nome acessível do <dialog> (aria-label em vez de aria-labelledby) — mesmo padrão já usado em Icon/Avatar/Badge pra 'texto visível OU rótulo acessível explícito, nunca nenhum dos dois'.
- CONSIDERADO E DESCARTADO — variações de footer com contagem fixa de botões (1/2/3), sugeridas pelo usuário com ressalva de que talvez não fosse necessário. Decisão: não implementar como prop/slot. Motivo: children já é livre (ver decisão de 'sem slot fixo de footer' acima) — 1, 2 ou 3 Button's dentro de um <div style={{display:'flex', gap:...}}> já resolve isso sem nenhuma API nova; uma prop 'footerVariant' seria uma reimplementação mais rígida do que já existe de graça via composição. Se surgir um padrão visual realmente repetitivo entre Modals reais (não hipotético), reconsiderar como um componente auxiliar (ex.: 'ModalActions'), não como prop do Modal.
- role=alertdialog como prop opcional (não o padrão) — a maioria dos Modals deste harness provavelmente é do tipo 'fluxo/edição', não 'alerta crítico'; forçar alertdialog sempre anunciaria com urgência exagerada casos que não precisam disso. Quem abre um Modal de confirmação destrutiva passa role='alertdialog' explicitamente.
- Tamanhos (small=400/medium=560/large=720px) sempre com teto de calc(100vw - espaco-g×2) — mesmo padrão responsivo já usado no ContractDialog interno, garante que o Modal nunca estoura a viewport em telas pequenas mesmo no tamanho 'large'.
- Sem prop 'initialFocusRef' ou similar pra customizar o elemento que recebe foco ao abrir — o comportamento nativo do showModal() (foca o primeiro elemento focável, ou o próprio <dialog> se não houver nenhum) já é adequado pra maioria dos casos; se um caso real pedir foco customizado, é decisão nova.
- Foco retorna pro elemento que abriu o Modal ao fechar — comportamento nativo do close() em navegadores modernos, não precisou de nenhuma lógica adicional pra implementar.
- BUG REAL corrigido em teste no navegador (modo escuro) — .dialog nunca declarava background/color próprios; o <dialog> nativo tem um fundo branco (ou 'Canvas', dependendo do navegador) no user-agent stylesheet por padrão, então o Modal continuava com o card claro mesmo no tema escuro, mesmo com o resto da página já correto. Adicionado `background: var(--fundo-superficie); color: var(--texto-primario)` explícitos em .dialog — os dois já eram tokens corretos, só faltava declará-los (o :root[data-theme] já cuidava do valor certo por tema, o componente só não estava lendo).

### Otp

- length é uma prop numérica simples (default 6, o tamanho mais comum de OTP), não um array de configuração por caixa — todas as caixas são idênticas, não há necessidade real de customizar uma caixa individualmente.
- onComplete é opcional e separado de onChange — onChange já entrega a string completa a cada mudança (inclusive quando bate length), mas nomear a intenção 'terminou de digitar, pode validar agora' evita o consumidor comparar value.length === length toda vez manualmente. Mesmo espírito de ter uma prop dedicada em vez de forçar lógica repetida em quem consome (parecido com onExport do Datatable já receber os dados prontos em vez de o consumidor recalcular).
- Colar preenche todas as caixas de uma vez a partir da primeira caixa focada, ignorando caracteres não-numéricos da string colada — comportamento padrão de mercado (a maioria dos apps de 2FA envia um SMS tipo 'Seu código é: 123456', colar a mensagem inteira ainda deveria funcionar, então a filtragem de não-dígitos é obrigatória, não opcional).
- Backspace em caixa vazia apaga e volta pra caixa anterior (padrão universal já estabelecido por outros produtos) — sem essa regra, apagar um código inteiro exigiria clicar em cada caixa manualmente.
- Sem estado 'focus' nem 'readOnly' no enum de state (diferente de TextField) — foco é uma propriedade de cada caixa individual, não do grupo inteiro, e readOnly não tem um caso de uso real pra um código de verificação (ou o campo está editável, ou está disabled).
- Tipografia texto-g-forte (maior, negrito) pro dígito dentro da caixa — mesmo racional visual já usado em outros contextos de 'poucos caracteres importantes' do harness, prioriza legibilidade de um código curto sobre a densidade de texto normal.
- BUG REAL corrigido em uso real (TwoFactorScreen) — onComplete originalmente disparava sem argumento (assinatura () => void), então quem consome precisava ler seu PRÓPRIO state (ex.: um value espelhado via useState) dentro do handler. Como onComplete é chamado SINCRONAMENTE logo depois de onChange (mesmo tick, antes do componente pai re-renderizar), esse state ainda estava com o valor ANTERIOR (closure obsoleta) — colar um código válido de 6 dígitos disparava onComplete, mas o handler via o value antigo (vazio) e reportava 'código inválido' incorretamente. - AJUSTADO a pedido do usuário — fundo do campo trocado de semantic.fundo-superficie pra semantic.fundo-campo (token novo): 'o fundo dos inputs de forma geral, devem ser levemente mais escuros que a cor de fundo da página onde estão, para destacar melhor'. No modo claro fundo-campo é idêntico a fundo-superficie (sem mudança visual, branco com borda já bastava) — só no modo escuro os dois valores divergem (fundo-campo um degrau mais escuro que a página), porque era só ali que o campo ficava indistinguível da própria página por trás.

### Pagination

- Extraído como componente novo, NÃO como refatoração da paginação já existente dentro da Datatable — a paginação da Datatable já está construída, testada e documentada (ver datatable.contract.json); reescrevê-la pra consumir este componente novo é dedup especulativo sem um bug ou necessidade real puxando essa mudança agora (mesma disciplina de 'no premature dedup' já aplicada a outras partes do harness). Os dois compartilham o mesmo desenho visual por replicação deliberada, não por código compartilhado.
- Seletor de itens por página é opt-in via presença de onPageSizeChange (sem a prop, o controle nem renderiza) — mesmo padrão já usado em Datatable pra bulkActions/toolbarActions: a prop decide SE um pedaço da UI aparece, não um boolean redundante tipo showPageSizeSelector.

### PasswordStrengthMeter

- Heurística SIMPLES e visual (conta critérios atendidos: comprimento ≥ 8, minúscula, maiúscula, dígito, símbolo → mapeia pra 5 níveis) — NÃO é um cálculo de entropia criptográfica nem substitui validação de segurança de verdade no backend. Decisão explícita de manter o cálculo simples e auditável em vez de importar uma lib de estimativa de entropia (ex.: zxcvbn) sem um caso de uso real que peça essa precisão — mesmo racional de 'não trazer dependência nova sem necessidade comprovada' já aplicado ao Datatable (decisão de não trazer lib de PDF/planilha).
- value é só LIDO, nunca controlado — PasswordStrengthMeter não é um campo, é um indicador pareado; o TextField ao lado continua sendo a fonte de verdade do valor digitado.
- 4 segmentos na barra (não um número arbitrário maior) — granularidade suficiente pra comunicar progressão sem fingir uma precisão que a heurística simples não tem.
- role='status' com aria-live='polite' (não 'assertive') — mudança de força não é urgente o bastante pra interromper o que o leitor de tela está anunciando; 'polite' aguarda a pausa natural, mesmo padrão de baixa-urgência já usado em outros textos dinâmicos do harness.
- Sem prop de customização da lista de critérios nesta v1 (ex.: exigir símbolo específico) — a heurística é fixa; se surgir necessidade de regras configuráveis por projeto, é decisão nova.
- AJUSTADO a pedido do usuário — lista de requisitos fixos (mínimo 8 caracteres, maiúscula, minúscula, número, caractere especial) exibida por padrão (showRequirements=true), cada item com ícone check/x reagindo em tempo real. Não substitui a barra/rótulo (continuam a leitura rápida 'quão forte'), é um reforço explícito de QUAIS critérios faltam — útil quando o usuário não entende por que a senha está 'fraca'. Continua sendo só apresentação: a lista não bloqueia nem valida o TextField pareado, mesma regra já documentada (PasswordStrengthMeter nunca controla o campo).

### Popover

- CORRIGIDO — auditoria de A11y (2026-09-01): BUG REAL, o painel não estava envolvido em FloatingFocusManager (só useClick/useDismiss/useRole) — o próprio contrato já prometia "Esc fecha o painel e devolve o foco pro gatilho", mas sem FloatingFocusManager isso não é garantido: se o usuário tivesse tabulado pra dentro do conteúdo antes de fechar, o foco não retornava ao desmontar, caindo pro <body>. Corrigido envolvendo o painel em <FloatingFocusManager context={context} modal={false}> — modal=false porque Popover não bloqueia o resto da página (mesma classificação de Drawer modal=false).
- Construído AGORA como componente novo, sem refatorar Select/Tooltip/Datatable/Breadcrumb/DatePicker/TimePicker/DateTimePicker pra consumi-lo — cada um já tem sua própria integração de floating-ui testada e funcionando; migrá-los pra este átomo é dedup especulativo sem um bug real puxando a mudança agora (mesma disciplina já aplicada em Pagination vs. a paginação embutida da Datatable). Este Popover existe pra componentes NOVOS que ainda vão precisar dessa peça, não pra substituir o que já existe.
- Gatilho via children + cloneElement (mesmo padrão já usado em Tooltip), não um render-prop — mantém a mesma 'forma' de API que o resto do harness já usa pra esse tipo de wrapper, em vez de introduzir um segundo estilo de API só pra este componente.
- Estado aberto/fechado é interno ao Popover por padrão — mesmo racional de Select/ComboBox/Breadcrumb: é estado de UI transiente na maioria dos casos.
- EXTENSÃO a pedido do usuário — open/onOpenChange adicionados como controle OPCIONAL (padrão idêntico ao já previsto nesta decision antes de existir um caso real): TicketCard precisava fechar seu menu de ações (Duplicar/Habilitar-Desabilitar/Apagar/Editar/Ver detalhes) automaticamente depois de o usuário escolher um item, o que o estado 100% interno não permitia. Quando `open` não é passado, o comportamento é idêntico ao de antes (internalOpen); quando é passado, controla de fato — mesmo padrão de componente controlado-opcional já usado em Textarea (enforceMaxLength) e SelectableCard (selectedTone), nenhuma quebra de compatibilidade pros consumidores existentes (Datatable continua com sua própria integração de floating-ui, PopoverDemo continua funcionando sem passar open).
- EXTENSÃO a pedido do usuário — prop tone ('light' padrão | 'dark') adicionada porque o CallControlBar precisava que seus 3 popovers (dispositivo de mic/câmera, configurações) tivessem fundo escuro pra combinar com a cápsula escura de onde eles abrem — o painel branco padrão destoava visualmente de um gatilho que já vive numa superfície escura. Só resolve fundo/borda do PAINEL (fundo-invertido reaproveitado, nenhum token novo); Popover continua sem opinião sobre a cor do TEXTO dentro de content — cabe a cada consumidor com tone='dark' usar cores de texto claras no próprio conteúdo (mesmo racional de Popover nunca ter decidido tipografia/cor de texto, só o invólucro).
- role é uma prop de enum fechado (dialog/menu/listbox) que alimenta useRole do floating-ui, em vez de Popover não ter role nenhum — dá ao consumidor a semântica ARIA certa pro tipo de conteúdo sem precisar reimplementar a integração com useRole por fora.
- Sem seta/arrow apontando pro gatilho (diferente de Tooltip) — arrow é uma decisão visual específica de Tooltip (baloon curto, precisa indicar de onde veio); painéis maiores (menu, formulário) tipicamente não usam esse recurso. Se um consumidor real precisar, pode compor a própria seta dentro de content.
- Navegação por teclado DENTRO do painel (setas, roving tabindex) não é responsabilidade do Popover — o conteúdo é livre (content), então cada consumidor decide sua própria navegação interna (ex.: um menu de ações usaria roving tabindex próprio, uma lista de opções usaria outro padrão) — mesmo racional de TabPanel não saber nada sobre o que tem dentro.
- LIMITAÇÃO CONHECIDA (mesma já documentada implicitamente em Tooltip) — children precisa ser um elemento que aceite ref e spread de props (ref, onClick, aria-expanded, aria-haspopup) diretamente, ex.: um <button> nativo. O átomo Button do harness tem API fechada (ButtonProps não inclui ref nem onClick, só onPress, e não faz spread de props desconhecidas no <button> interno) — por isso NÃO funciona como filho direto de Popover (nem de Tooltip). Confirmado testando no navegador: usar <Button> como children resultava em aria-expanded/aria-haspopup nunca aplicados e o clique nunca abrindo o painel, sem nenhum erro visível. Consumidores que precisam de um gatilho com a aparência de Button devem usar um <button> nativo estilizado (ou compor visualmente parecido com Button), não o componente Button em si — mesma solução já adotada no demo do Tooltip.
- BUG REAL corrigido a pedido do usuário — o painel flutuante (FloatingPortal) renderiza fora da árvore de DOM estilizada do app (nó solto no fim do <body>), então conteúdo livre (`content`) que dependesse de herança normal de font-family (ex.: `font: inherit` num <button> dentro do content) caía pra fonte padrão do navegador — html/body não define font-family nenhuma no harness (cada componente declara a própria, ver base.css). Sintoma real: os itens de menu do 'User Card' (SideNavDemo/BackofficeTemplate) apareciam numa fonte diferente do resto da interface. Corrigido definindo font-family/font-size (texto-p) direto no `.popover` (o próprio painel), mesmo racional do fix de cor já existente em base.css pra Drawer/Modal — dá um valor padrão sensato pra QUALQUER conteúdo livre dentro do popover, sem depender de cada consumidor lembrar de declarar font-family manualmente. Conteúdo que já declara a própria fonte (ex.: StackedText, que sempre define texto-p/texto-micro) continua intacto — sobrescreve o padrão normalmente, é só um fallback pra quem não declara nada.

### ProgressBar

- value fora do intervalo [0, max] é CLAMPADO (não lança erro) — ex.: value=150 com max=100 vira 100% visualmente. Motivo: cálculos de progresso vindos de APIs externas (ex.: bytes enviados / bytes totais) podem momentaneamente passar de 100% por arredondamento; travar a UI com um erro de execução por causa disso seria pior que simplesmente exibir 100%.
- variant tem só 3 opções (primary/success/error), não os 5 do Badge/Chip (sem info/warning) — decisão do agente, não perguntada pra reduzir interferência: uma barra de progresso normalmente só precisa comunicar 'em andamento' (primary), 'terminou bem' (success) ou 'falhou' (error); 'aviso'/'info' não têm um significado claro no contexto de uma operação em progresso. Se surgir um caso real, é decisão nova.
- EXTENSÃO — 3 novos variants (warning/critical/neutral), a partir da análise de sistemas legados (ver analise-sistemas-legados.md, item 1.7 'Barra de progresso rotulada com contagem') e da molécula ProgressList que passou a consumir ProgressBar (ver contratos/progress-list.contract.json). Motivo: o caso real observado não é 'uma barra de operação em andamento' (o que a decisão original cobria bem com só 3 variants), é uma LISTA de barras representando categorias de prioridade/status lado a lado (ex.: 'No prazo'/'Atenção'/'Urgente'/'Atrasado') — mesma semântica de severidade já usada em badge.contract.json (que ganhou os mesmos 3 tons na mesma leva de mudanças: warning=borda-aviso, critical=acao-destrutiva-pressionada, mais 'neutral'=borda-inativo, novo tanto pro Badge quanto pro ProgressBar). Reaproveita exatamente os mesmos tokens já usados no Badge (nenhum token novo criado) — mantém as duas famílias de componente com a mesma paleta de severidade. Continuam fora do ProgressBar: 'info' (ainda sem um caso real de progresso ou lista de prioridade que precise dele) e qualquer variant fora dessa paleta de status/severidade (ex.: cores puramente categóricas sem relação com prioridade/urgência, vistas em outros blocos das telas legadas mas sem padrão consistente o bastante pra virar token — ver analise-sistemas-legados.md pro racional completo).
- accessibleLabel é OBRIGATÓRIO (diferente de outros 'accessibleLabel' opcionais no harness) — uma barra de progresso sozinha (só cor + largura, às vezes sem showValue) não tem NENHUM outro jeito de comunicar o que está progredindo pra quem usa leitor de tela; diferente de Icon/Avatar, que têm fallback de name/children, ProgressBar não tem nenhuma fonte alternativa de contexto.
- showValue mostra só o número (ex.: '42%'), não reaproveita accessibleLabel como texto visível — são propósitos diferentes: accessibleLabel é pro leitor de tela entender O QUE é a barra, showValue é pra qualquer pessoa ver QUANTO já foi. As duas informações já ficam disponíveis juntas pra quem usa leitor de tela via aria-valuenow + aria-label, sem precisar duplicar na tela visualmente.
- Sem tamanhos (small/medium/large) neste contrato — uma altura fixa e discreta (mesmo espírito de simplicidade do Divider) até surgir um caso real que peça variação.

### ProgressList

- Nasceu da análise de sistemas legados (analise-sistemas-legados.md, item 1.7) — o padrão 'rótulo — barra colorida — contagem' aparecia repetido 4 vezes só no dashboard do Credenciamento (Prioridade, Tempo médio por status, Rede de atendimento, Regime de atendimento), sempre remontado na mão.
- accessibleLabel de cada ProgressBar interno é derivado automaticamente como `${label}: ${count}` — ProgressList não expõe uma prop accessibleLabel por item pro consumidor preencher, porque label+count já formam a descrição completa sozinhos (mesmo racional de DataField não precisar de aria-label extra: a relação rótulo→valor já está no DOM). Reduz a chance de esquecer de preencher o accessibleLabel obrigatório do ProgressBar em cada item de uma lista longa.
- count é sempre uma STRING pronta (não um number formatado pelo componente) — mesmo racional de DataField.value: ProgressList não sabe se o consumidor quer '50', '50 Qt', '50%' ou '50 registros', então não assume formato nenhum.
- variant é opcional por item (default 'primary', do próprio ProgressBar) — pensado especificamente pra listas de prioridade/severidade usarem neutral/warning/error/critical (variantes que ProgressBar ganhou nesta mesma leva de mudanças, ver contratos/progress-bar.contract.json decisions) mas não é obrigatório: uma lista de categorias sem conotação de severidade (ex.: 'Rede de atendimento') pode deixar todo item com o primary padrão ou passar 'success' pra todos.
- Sem prop de título/cabeçalho do bloco inteiro (ex.: 'Prioridade') — ProgressList é só a lista em si; o título do bloco é responsabilidade de quem consome (ex.: um <h3> ou StatCard por fora), mesmo racional de Timeline não ter título embutido.
- Layout de 2 linhas por item (rótulo em cima, barra+contagem embaixo) em vez de 1 linha só (rótulo — barra — contagem lado a lado) — reflete fielmente o padrão visual observado nos prints legados, e dá mais espaço horizontal pra barra em rótulos longos sem espremer a barra.
- BUG REAL corrigido em teste no navegador — a raiz do componente (<ul class='list'>) não tinha width:100%. Como o Playground usa um wrapper de demo com `align-items: center` (que faz filhos flex SEM largura explícita encolherem ao próprio conteúdo, em vez de esticar), a lista inteira colapsava pra poucos pixels de largura, e cada ProgressBar interno virava um pontinho quase invisível em vez de uma barra proporcional. `flex: 1` no wrapper da barra (dentro de `.row`) não bastava sozinho, porque o problema começava um nível acima: sem uma largura de referência na raiz, não havia espaço nenhum pra distribuir entre os itens de `.row`. Corrigido adicionando `width: 100%` em `.list` — mesma técnica que o próprio ProgressBar já usa na raiz do seu wrapper (contratos/progress-bar.contract.json não documentava isso explicitamente porque nunca tinha quebrado antes; ProgressList herdou o mesmo raciocínio agora, documentado aqui pra não se perder de novo). Lição pro harness: qualquer componente cuja raiz precisa ocupar a largura do container (não só encolher ao conteúdo) precisa de width:100% explícito na raiz — não é suficiente só os filhos internos terem flex:1, sem uma largura de referência acima deles.

### RadioGroup

- RESOLVIDO — RadioGroup existe porque Radio/HelperText já registravam essa lacuna como dívida técnica (ver radio.contract.json, decisions: 'RadioGroup não existe... candidato natural quando surgir um caso real'). Este contrato preenche exatamente o que Radio previu: state=error compartilhado, HelperText uma vez só, e agora também name automático.
- name é OPCIONAL aqui (gerado via useId se omitido) — diferente do Radio isolado, onde name é sempre obrigatório (porque um Radio sozinho não tem como saber se faz parte de um grupo formal ou não). RadioGroup, por definição, SEMPRE representa um grupo — não faz sentido pedir pra quem consome inventar um name toda vez.
- Legend usa a tipografia de type-style.texto-rotulo-campo (a mesma do FieldLabel), mas NÃO reaproveita o componente FieldLabel em si — FieldLabel tem ícone opcional + Tooltip de ajuda, funcionalidade que um <legend> de fieldset não precisa neste primeiro momento; reaproveitar o componente inteiro traria complexidade (Tooltip dentro de <legend> tem suporte inconsistente entre navegadores). Se surgir um caso real de RadioGroup com tooltip de ajuda, é decisão nova.

- disabled é por option (não uma prop do grupo) — via options[i].disabled, repassado Radio a Radio. Não existe uma prop 'disabled' no nível do RadioGroup inteiro neste contrato; se precisar desabilitar o grupo inteiro, quem consome marca todas as options como disabled (mecanicamente simples, sem precisar de um caminho especial).
- AJUSTADO a pedido do usuário — nova prop 'orientation' (vertical/horizontal, default vertical). horizontal usa flex-direction: row + flex-wrap: wrap (não uma grid fixa de N colunas) — o grupo simplesmente quebra pra próxima linha quando os labels não cabem na largura disponível, sem exigir que quem consome calcule quantas colunas cabem. Espaçamento horizontal entre opções usa espaco-m (mais generoso que o espaco-xp vertical original) porque, lado a lado, opções muito próximas ficam mais difíceis de escanear como itens distintos do que empilhadas.

### Rating

- CORRIGIDO — auditoria de contratos (2026-09-01): border (borda-foco) e radius (raio-xp) adicionados — o anel de foco visível de cada estrela usa outline com esses dois tokens, categorias que não estavam declaradas em tokensAllowed.
- role="slider" no modo interativo em vez de radiogroup de N opções — motivo prático: com allowHalf, os valores possíveis (0, 0.5, 1, 1.5...max) formam uma escala contínua o bastante que um slider comunica melhor via aria-valuetext do que N inputs de rádio individuais rotulados; sem allowHalf, ainda funciona bem porque um slider com step=1 é semanticamente equivalente a escolher entre max opções discretas.
- readOnly vira role="img" (não slider, não radiogroup) — quando o valor é só exibido (ex.: nota média de um produto), não existe nenhuma ação possível, então a semântica correta é 'imagem informativa com texto alternativo', igual a qualquer outro indicador visual não-interativo do harness.
- Meio-ponto detectado pela metade clicada de CADA estrela (esquerda=X.5, direita=X inteiro), não por um clique-e-arraste tipo slider real — mantém a interação simples (um clique só) e visualmente óbvia (a estrela sob o cursor já mostra o preview do valor ao passar o mouse, sem precisar arrastar).
- onChange vira proibido (não só opcional) quando state='readOnly' — reforça a mesma regra que Card já segue (não misturar 'isso é puramente estrutural/informativo' com 'isso reage a interação'), documentado explicitamente em vez de deixar implícito.
- Ícone star-half só aparece na posição exata onde value cai no meio (ex.: value=3.5 → estrelas 1-3 cheias, estrela 4 usa star-half, estrela 5 vazia) — nunca combinando duas estrelas parciais nem tentando simular frações menores que 0.5, porque não há um caso de uso real que peça granularidade maior.

Motivo: só trocar a cor do contorno (weight='regular') não gerava contraste visual suficiente entre marcada/não-marcada à distância; o preenchimento sólido é o padrão de mercado pra esse tipo de indicador e ficou mais legível. - AJUSTADO a pedido do usuário — color='yellow' trocado de semantic.icone-aviso (Amarelo/amarelo-700, #9B610D — um tom mostarda/marrom escuro na escala primitiva) para semantic.borda-aviso (Amarelo/amarelo-500, #EBB612 — um amarelo-ouro bem mais claro e saturado). Motivo: icone-aviso foi desenhado pra texto/ícone pequeno sobre fundo claro (precisa de mais contraste, por isso é escuro), mas pra uma estrela preenchida grande o resultado lia como 'marrom', não 'amarelo'. borda-aviso já existe no harness com esse tom mais claro (reaproveitado também em Avatar, Alert e PasswordStrengthMeter como indicador visual, não só como cor de borda) — nenhum token novo precisou ser criado.
- AJUSTADO a pedido do usuário — no display='compact', o TEXTO do value (ex.: '4.8') usa semantic.texto-aviso (Amarelo-700, #9B610D — o mesmo tom mostarda escuro que foi trocado na estrela pela decisão acima) em vez de borda-aviso, só quando color='yellow'. Motivo: o mesmo amarelo-500 que funciona bem numa estrela preenchida grande (weight='fill', área grande de cor sólida) fica claro demais pra ler como texto pequeno — texto precisa de mais contraste que uma forma sólida grande pra ser confortável de ler. color='green' não teve esse problema (acao-primaria já tem contraste suficiente pra texto), então só a combinação display='compact' + color='yellow' usa uma cor de texto diferente da cor do ícone.
- AJUSTADO a pedido do usuário — nova prop 'size' (default/large) reaproveitando icone-medio/icone-grande já existentes no Icon, em vez de expor um valor numérico livre — mantém o componente preso à escala de tamanhos do harness (mesmo racional já aplicado a outras props de tamanho no design system, ex.: Switch/Avatar).
- AJUSTADO a pedido do usuário — nova prop 'display' (stars/compact), só válida com state='readOnly': compact resolve o caso 'só quero mostrar a nota, sem ocupar o espaço de max estrelas' (ex.: dentro de uma linha de Datatable, um card compacto) — 1 estrela cheia (sempre weight='fill', sempre a cor escolhida em 'color') + o texto do value formatado (ex.: '3.5', usando toFixed(1) só quando o value tem parte fracionária, senão mostra inteiro) em type-style.texto-m-forte. Não existe versão interativa de display='compact' (ver forbidden) — clicar numa estrela única pra abrir/editar a nota completa não é um padrão de interação que o harness precisa resolver agora; se aparecer um caso real, é decisão nova.

### Skeleton

- aria-hidden sempre true, sem opção de desligar — Skeleton nunca carrega informação real, decisão fechada (diferente de Icon, que tem um modo não-decorativo opcional). Se a região toda precisa anunciar 'carregando' pra leitor de tela, isso é responsabilidade de quem consome (role=status/aria-busy no container pai), não do Skeleton individual — mesmo princípio de 'Skeleton não sabe nada sobre o contexto ao redor' já usado em Divider/Badge (position exige que o pai monte o contexto).
- Altura padrão por shape quando height é omitido: text=16px (aprox. 1 linha de texto-m), circle=40px (mesmo diâmetro do Avatar medium), rect=120px (altura arbitrária razoável pra um placeholder de card/imagem, ajustável via prop). Documentado explicitamente porque são valores fixos não-tokenizados (mesma disciplina já usada nas constantes de 1-2px de borda em outros contratos) — não existe token estrutural dedicado a 'altura de skeleton'.
- Animação de pulso (opacity 1↔0.5, alternando) implementada via CSS @keyframes, envolvida em @media (prefers-reduced-motion: reduce) que desativa a animação — primeira vez que esse critério de acessibilidade aparece explicitamente num contrato deste harness (os outros componentes não têm animação própria pra precisar disso).
- Cor única (semantic.acao-inativa) pra todos os shapes — Skeleton não tem variant de cor/intent, é sempre neutro; não faz sentido comunicar status (erro/sucesso) num placeholder de conteúdo que ainda nem chegou.
- width/height sem valor padrão pra width (sempre explícito pelo consumidor) — Skeleton não tem como adivinhar a largura do texto/imagem real que vai substituí-lo; só a altura tem um padrão razoável por shape.

### Slider

- Baseado em <input type='range'> NATIVO (um no modo único, dois empilhados no modo range) em vez de um thumb customizado arrastável via mouse/touch handlers manuais — decisão de acessibilidade: o navegador já resolve teclado (setas, Home/End, Page Up/Down), foco e leitura de tela pra esse elemento de graça; reimplementar do zero só pra ter controle visual total reintroduziria bugs que o próprio browser já não tem.
- Modo range usa dois inputs nativos EMPILHADOS (mesma técnica de mercado consolidada pra dual-range slider: os dois cobrem a mesma área, cada um com pointer-events só no próprio thumb via CSS, o restante da trilha é 'furado' pra clique) — a alternativa de um único input controlando dois valores não existe nativamente em HTML, então dois inputs reais é o caminho que preserva acessibilidade nativa nos dois cabos.
- onChange no modo range sempre entrega a tupla já ordenada e sem cruzamento — ao mover o cabo 'mínimo' além do valor atual do 'máximo' (ou vice-versa), o componente clampa o valor no lugar do outro cabo em vez de deixar cruzar, evitando um estado visualmente ambíguo (dois cabos na mesma posição sinaliza 'intervalo de largura zero', nunca 'trocado').
- Sem state='error' — diferente de TextField/Select, um slider não tem como o usuário produzir um valor 'inválido' através da própria interação (arrastar sempre resulta num número dentro de [min,max]); se um valor inicial inválido vier de fora, isso é um erro de quem consome, não um estado visual do componente.
- showValue (texto do valor atual) é true por padrão — sliders sem indicação numérica visível são mais difíceis de usar com precisão; false é o opt-out pra quando o próprio contexto já mostra o valor de outra forma (ex.: preview ao vivo em outro lugar da tela).
- AJUSTADO a pedido do usuário — thumb passou de contorno (fundo branco + borda verde) pra PREENCHIDO (fundo semantic.acao-primaria + anel branco de 2px + contorno verde de 1px por fora, via box-shadow). Motivo: o contorno sozinho tinha pouco destaque visual sobre a trilha; o preenchimento sólido deixa o alvo de arraste mais evidente. Estado disabled preenche com semantic.texto-inativo em vez de acao-primaria, mantendo a mesma forma (preenchido + anel), só trocando a cor.

Corrigido tirando o iconCircle do fluxo flex (position:absolute, ancorado no canto superior direito do header, que virou position:relative) — a altura do cabeçalho passa a ser SEMPRE só a do texto do label, com ou sem ícone, garantindo o mesmo gap label→valor nos dois casos. .header ganha padding-right (só quando icon está presente, via classe condicional) pra reservar o espaço do círculo e não deixar o texto do label passar por baixo dele.

### Stepper

- PERGUNTADO AO USUÁRIO (indiretamente, por conflito de nome) — este componente nasceu do pedido de 'acompanhamento de etapas tipo passo a passo de formulário, com indicador numérico ou ícone, texto principal e secundário'. Já existia um átomo chamado Stepper (quantidade com +/-); renomeado pra QuantitySelector (ver quantity-selector.contract.json) especificamente pra liberar este nome, porque 'Stepper' é o termo padrão de mercado pra indicador de etapas — preservar o nome mais reconhecível pro componente mais alinhado com a convenção do que pro que chegou primeiro.
- Indicador numérico OU ícone é uma escolha POR ETAPA (items[].icon), não uma prop global do Stepper inteiro — um fluxo real pode querer ícones só nas etapas que têm um símbolo óbvio (ex.: cartão de crédito pra 'Pagamento') e número nas demais. Etapa completed sem icon customizado ganha uma marca de concluído automática (check) — padrão de mercado quase universal, evita forçar o consumidor a passar icon='check' manualmente em toda etapa só pra ter esse comportamento esperado.
- Só 3 estados (pending/current/completed) derivados PURAMENTE de currentStep vs. o índice de cada etapa — sem um 4º estado 'error/inválida' nesta v1 (ex.: etapa com validação que falhou). Não foi pedido; se surgir caso real, é decisão nova (provavelmente items[].error?:boolean).
- onStepClick só habilita clique em etapas completed/current, nunca pending — mesmo racional de 'não adivinhar/pular à frente' já usado em Select/ComboBox (navegação por teclado pula itens disabled). Sem onStepClick, o componente é 100% estático/informativo — a orquestração de navegação de verdade (validar a etapa atual antes de deixar avançar, etc.) é responsabilidade do organismo Wizard, não deste indicador.
- aria-current="step" (não "page") — token correto da especificação ARIA especificamente pra indicadores de progresso sequencial (steps/wizards), diferente do aria-current="page" já usado em Breadcrumb (último item) e NavBar/Link (prop current, ver link.contract.json).
- Só horizontal nesta v1 — mesmo racional já usado em Tabs/NavBar (vertical fica pra quando um caso de uso real pedir, não construído especulativamente).
- structural.espaco-g entrou em tokensAllowed.spacing — largura mínima do conector entre etapas (evita conectores colapsados demais em telas estreitas com labels curtos).
- Wizard (organismo separado, fila do roadmap) reaproveita Stepper como o indicador visual, mas não faz parte deste contrato — Stepper nunca sabe о que está sendo validado ou quando avançar; ele só reflete um currentStep que já vem pronto de fora.
- BUG CORRIGIDO (teste em navegador) — item.icon numa etapa 'current' ficava invisível: a cor do ícone usava sempre semantic.acao-primaria-texto (pensada pro marcador 'completed', que tem fundo preenchido com acao-primaria), mas o marcador 'current' não tem fundo preenchido (só borda) — resultado era ícone claro sobre fundo claro. Corrigido pra cor do ícone acompanhar o estado do marcador: completed usa acao-primaria-texto (fundo preenchido), current usa semantic.acao-primaria (mesma cor do texto/borda do marcador current), pending usa semantic.icone-secundario.
- AJUSTADO a pedido do usuário — duas variantes visuais explícitas em vez de uma única aparência fixa: 'inline' (texto ao lado do marcador, sem conector — itens ficam do tamanho do próprio conteúdo, mais compacto pra poucos passos curtos) e 'stacked' (conector ligando os marcadores, texto abaixo — itens dividem a largura igualmente, mais legível quando há vários passos lado a lado, ex.: dentro do Wizard). default='stacked' porque preserva o racional visual original do componente (conector sempre existiu); 'inline' é o opt-in pra quando o espaço horizontal for mais escasso ou os labels forem curtos o bastante pra caberem ao lado do marcador sem quebrar a leitura. A lógica de estado (pending/current/completed), navegação (onStepClick) e aria-current continuam idênticas nas duas variantes — só a disposição visual muda.

### Switch

- RESOLVIDO — bug real encontrado numa Datatable com Switch 'nu' (sem label, via accessibleLabel) na coluna de ações: a linha da tabela não encolhia em densidade condensed. Causa raiz: .row tinha min-height:44px em content-box (padrão do CSS), e .bare somava seu padding vertical (espaco-pp em cima + embaixo) POR CIMA desse valor, resultando em 60px reais em vez dos 44px pretendidos — o comentário original de .bare já dizia 'garante os 44×44px', mas o box model errado deixava passar pra 60. Corrigido com box-sizing:border-box em .row, fazendo o padding de .bare contar DENTRO do orçamento de 44px, não somar em cima. Acontecia em qualquer Switch sem label (medium ou small), não é específico de size='small' — só ficou visível ao medir pixel a pixel numa tabela tentando encolher.
- RESOLVIDO com o usuário — label é opcional (diferente de Checkbox/Radio, onde é sempre obrigatório): Switch é comumente usado 'nu' dentro de uma linha de lista de configurações onde o texto já existe fora do componente (ex.: uma linha com 'Notificações por e-mail' + o Switch alinhado à direita, onde o texto da linha inteira já é o rótulo). Quando label é omitido, accessibleLabel é obrigatório — impede um Switch sem nome acessível.
- RESOLVIDO com o usuário — sem state=error/HelperText (diferente de Checkbox): Switch representa uma ação instantânea que já aplicou o efeito assim que o usuário interagiu, não um valor pendente de validação/submit. Se a ação falhar (ex.: erro de rede ao salvar a preferência), a comunicação é responsabilidade de um Toast/mensagem externa ao componente, não de um estado embutido no Switch — mesmo raciocínio já usado para não dar RadioGroup especulativo ao Radio.
- RESOLVIDO com o usuário — dimensões derivadas dos tokens estruturais existentes, já que não há token dedicado de trilho/thumb no tokens.json (diferente do Checkbox, que reaproveita icone-medio direto pra caixa): thumb = structural.icone-medio (20px, mesmo valor usado no círculo do Radio). Trilho: altura = icone-medio + 2×espaco-xp (20 + 8 = 28px), largura = 2× a altura (56px). Deriva inteiramente de tokens já existentes, não introduz nenhum valor cru novo — mesma disciplina já registrada nas decisions do Checkbox/Radio.
- role=switch em cima de <input type="checkbox"> nativo, não um <button role="switch"> customizado — mantém a mesma base de Checkbox/Radio (input nativo escondido + span decorativo aria-hidden), reaproveita o comportamento de teclado/toggle do checkbox nativo em vez de reimplementar aria-checked manualmente num button.
- Cor do trilho ligado reaproveita semantic.acao-primaria, mesmo token que Checkbox usa pro fundo marcado — não cria uma família nova de cor 'ligado' separada da família de seleção já estabelecida.
- Cor do trilho desligado (habilitado) usa semantic.fundo-secundario + borda semantic.borda-base — deliberadamente diferente de semantic.acao-inativa (reservada para o estado disabled, mesmo padrão do Checkbox/Radio) pra não confundir visualmente 'desligado, mas ainda usável' com 'desabilitado'.
- Thumb é sempre semantic.fundo-superficie (branco), em todos os estados (ligado/desligado/disabled) — a posição do thumb (esquerda/direita) já comunica o estado por si só, diferente do Checkbox que precisa trocar a cor do glifo porque o ícone de check é a única pista visual.
- Borda do trilho fixa em 2px — não é token, mesma constante não-tokenizada já usada na caixa do Checkbox/círculo do Radio.
- REVISADO — size='small' adicionado a pedido do usuário pra caber na coluna de ações de datatable.contract.json (trilho medium ficava desproporcional numa célula de tabela densa). Dimensões seguem a mesma fórmula do medium, só trocando o token do thumb: thumb=structural.icone-pequeno (16px em vez de 20px), trilho altura=thumb+2×espaco-xp (24px), largura=2×altura (48px) — nenhum valor cru novo, mesma disciplina de derivação do medium. O alvo de toque de 44×44px continua garantido via padding invisível no <label>, não relaxado — só o desenho visual muda de tamanho.

### Tabs

- Ativação AUTOMÁTICA (seta já troca a aba ativa, sem precisar de Enter/Espaço) em vez de manual — decisão do agente, não perguntada ao usuário pra reduzir interferência: é o padrão mais comum (abas de navegador, a maioria dos design systems) e o conteúdo de cada painel neste harness é tipicamente leve (não há custo real de carregamento que justificasse a ativação manual, que existe principalmente pra evitar carregar conteúdo caro a cada tecla de seta). Revisitar se surgir um caso real de painel caro de renderizar.
- items é um array de dados (value/label/disabled), não children JSX livre — Tabs não aceita um <Tab> customizado por fora. Mesmo padrão de 'fonte única, sem slot arbitrário' já usado em Select (options) e Card (sem slots fixos, mas aqui pelo motivo oposto: a estrutura do tablist É rígida o bastante pra não precisar de flexibilidade).
- TabPanel é um componente separado (não um slot interno de Tabs) que o consumidor posiciona e conecta via o mesmo value — Tabs não sabe nada sobre o conteúdo dos painéis, só sobre a lista de abas. Motivo: manter Tabs 100% desacoplado de LAYOUT do conteúdo (poderia ser abaixo, ao lado, em outra ordem do DOM) — mesmo racional de HelperText/FieldLabel serem componentes próprios em vez de slots fixos dentro de TextField.
- ids previsíveis (tab-{value} / panel-{value}) derivados diretamente do value da aba — evita gerar e sincronizar ids aleatórios entre dois componentes desacoplados (Tabs e TabPanel) que não compartilham estado React entre si além do value que já vem de fora.
- Só horizontal neste contrato — Tabs vertical (comum em configurações estilo 'painel lateral') não tem caso de uso real ainda; se aparecer, é decisão nova, mesmo raciocínio já usado em outros contratos pra não construir variante sem pedido real (ex.: RadioGroup ainda não existe por esse motivo).
- count (indicador numérico por aba) reaproveita o átomo Badge com variant='neutral' fixo — não é uma prop de cor customizável por aba. Pedido explícito do usuário: 'usuário precisa saber quantos itens/registros tem naquela aba'. variant fixo em 'neutral' (não segue o estado selecionado/não-selecionado da aba) porque o Badge já tem contraste suficiente nos dois fundos e variar a cor por seleção seria uma segunda forma de indicar 'selecionado', redundante com a borda/cor que a aba já usa.
- aria-label combinando label+count é setado no <button> inteiro (sobrescrevendo o texto visível como nome acessível) só quando count existe — sem count, o texto do botão já é o nome acessível de sobra, não precisa de aria-label redundante.

### Textarea

- Sem leftIcon/rightIcon (diferente do TextField): um campo multi-linha não tem uma posição natural de 1 linha pra ancorar um ícone interno sem ele flutuar estranhamente ou sobrepor texto em wrap. Se surgir um caso real (ex.: ícone de anexo), é decisão nova, não uma adivinhação agora.
- AJUSTADO a pedido do usuário — a decisão anterior ('sem contador de caracteres nesta versão... candidato a entrar depois') foi revisada: CommentComposer (ver comment-composer.contract.json) trouxe o caso de uso real que faltava. Nova prop showCharacterCount (default false, opt-in) mostra 'N/max' no rodapé, alinhado à direita do HelperText — quando ausente, nada muda (comportamento idêntico ao anterior). Contador só aparece se maxLength também estiver definido (sem denominador não há o que mostrar).
- AJUSTADO a pedido do usuário — maxLength deixou de ser SÓ o atributo nativo; ganhou um modo de aplicação configurável via enforceMaxLength (default true = comportamento antigo, bloqueio rígido nativo). Motivo: o pedido do usuário incluía duas formas de lidar com o limite — 'bloqueando a digitação' (mapeia direto pro atributo nativo maxLength, já existia) OU 'permitindo digitar e alertando e bloqueando o botão' (exige que o USUÁRIO consiga digitar ALÉM do limite, o que o atributo nativo maxLength nunca permitiria por definição). enforceMaxLength=false resolve o segundo caso: maxLength continua existindo como número de referência (pro contador e pra quem consome decidir o que fazer quando ultrapassado), só não é mais aplicado como restrição física do navegador.
- Estado 'acima do limite' (count > maxLength) só é fisicamente alcançável com enforceMaxLength=false — com o padrão (true), o navegador nunca deixa a contagem passar de maxLength, então o contador nunca chega a ficar na cor de erro nesse modo. Isso é intencional, não uma inconsistência: o texto vermelho no contador é reforço visual do MESMO estado que enforceMaxLength=false already permite existir, não um estado novo e independente.
- resizable=true por padrão, e mesmo assim só CSS resize:vertical — nunca horizontal/both (quebraria o layout de formulários responsivos). resizable=false trava a altura em rows.
- rows (padrão 4) substitui a altura fixa de 44px que Button/TextField usam — não faz sentido forçar uma altura de alvo de toque numa caixa que já é naturalmente grande o suficiente por ser multi-linha; altura real é rows × altura de linha + padding.
- Reaproveita FieldLabel e HelperText exatamente como o TextField (mesmo padrão de id via useId, aria-describedby, withInfo/infoText) — nenhuma reimplementação.
- Foco + erro: erro vence visualmente — mesma regra já fixada em text-field.contract.json, aplicada aqui por consistência entre contratos de data-entry, não reaberta.
- AJUSTADO a pedido do usuário — fundo do campo trocado de semantic.fundo-superficie pra semantic.fundo-campo (token novo): 'o fundo dos inputs de forma geral, devem ser levemente mais escuros que a cor de fundo da página onde estão, para destacar melhor'. No modo claro fundo-campo é idêntico a fundo-superficie (sem mudança visual, branco com borda já bastava) — só no modo escuro os dois valores divergem (fundo-campo um degrau mais escuro que a página), porque era só ali que o campo ficava indistinguível da própria página por trás.

### TextField

- leftIcon e rightIcon são independentes e combináveis: dá pra ter só um dos dois ou os dois ao mesmo tempo (variant 'both-icons') — não é preciso escolher um lado só. Documentado explicitamente aqui porque só estava implícito na lista de variants.
- borda-base corrigido: apontava para cinza-800 (escuro demais) e estava invertido com borda-forte — agora aponta pro tom discreto correto.
- borda-foco corrigido: apontava para um cinza quase invisível — agora aponta pro verde-600 da marca.
- Foco + erro: erro vence (borda vermelha), mas o anel de foco continua visível.
- texto-placeholder é um token próprio (cinza-500), mais legível que texto-inativo.
- TextField gera seu próprio id via useId e conecta tudo internamente (htmlFor no FieldLabel, aria-describedby no input apontando pro id derivado do HelperText) — quem usa TextField nunca lida com ids.

- type=password NÃO virou um componente separado (ex.: 'PasswordField'): a única diferença real é o slot direito (toggle em vez de ícone estático) e o atributo type do <input> alternando entre 'password'/'text' — não há anatomia, token ou estado novo o suficiente pra justificar um contrato à parte. Reavaliar só se surgir um requisito que TextField genuinamente não cubra (ex.: indicador de força de senha).

- AJUSTADO a pedido do usuário — type='tel' agora aplica máscara automática de telefone brasileiro (formato progressivo: (DD) DDDD-DDDD pra 10 dígitos/fixo, (DD) DDDDD-DDDD pra 11 dígitos/celular — o split muda de 4 pra 5 dígitos assim que o 9º dígito do número é digitado). Lógica extraída pra src/components/shared/phoneMask.ts, mesmo racional de reaproveitamento já usado em dateTimeMask.ts pros pickers de data/hora — evita duplicar a função onlyDigits e a lógica de máscara caso outro componente precise formatar telefone no futuro.

NÃO é um seletor de país completo com lista/bandeira/código dinâmico — o harness inteiro já assume locale fixo pt-BR/Brasil em todo lugar que lida com formato (DatePicker sempre DD/MM/AAAA, Calendar sempre locale pt-BR), então um DDI fixo '+55' é consistente com essa decisão já tomada, não uma escolha nova. Se aparecer um caso real de formulário multi-país, é decisão nova (provavelmente um componente PhoneField dedicado, não uma prop a mais aqui).

Quem precisar só dos dígitos aplica o próprio replace(/\D/g, '') no value recebido.
- AJUSTADO a pedido do usuário — fundo do campo trocado de semantic.fundo-superficie pra semantic.fundo-campo (token novo): 'o fundo dos inputs de forma geral, devem ser levemente mais escuros que a cor de fundo da página onde estão, para destacar melhor'. No modo claro fundo-campo é idêntico a fundo-superficie (sem mudança visual, branco com borda já bastava) — só no modo escuro os dois valores divergem (fundo-campo um degrau mais escuro que a página), porque era só ali que o campo ficava indistinguível da própria página por trás.

Mesmo racional e mesma técnica já estabelecidos por type='tel': lógica extraída pra src/components/shared/cpfMask.ts (mesmo padrão de phoneMask.ts/dateTimeMask.ts — nunca duplicar a função onlyDigits), aplica só dígitos e insere pontuação progressivamente conforme o usuário digita (sem exigir um separador manual). Sem validação de dígito verificador (algoritmo de CPF válido) nesta v1 — TextField mascara o FORMATO, não valida se o número é um CPF real; validação de conteúdo é responsabilidade de quem consome (ex.: no submit do formulário), mesma fronteira já estabelecida pro resto do harness (Checkbox 'required' não valida se marcado É a resposta certa, só que foi marcado).

### TicketCard

### Timeline

- Puramente informativo, sem interatividade nem estados 'atual/pendente' — diferente de Stepper (que modela progresso vivo de um fluxo), Timeline modela HISTÓRICO já acontecido; um evento não 'está em andamento', ele já ocorreu ou não existe na lista.
- tone por item (não um enum fixo de estado como completed/current/pending do Stepper) — cada evento do histórico pode ter uma conotação própria (sucesso, erro, aviso, informativo, neutro) independente da posição na lista, diferente de Stepper onde o estado é derivado da posição relativa a currentStep.
- Marcadores sempre aria-hidden — a cor/ícone é reforço visual, nunca a única pista (mesmo racional de contraste-mínimo de Alert/Badge já aplicado no resto do harness).
- Sem paginação/virtualização nesta v1 — histórico muito longo (centenas de eventos) não foi um caso de uso real ainda; se aparecer, é decisão nova (provavelmente reaproveitando Pagination por fora, não construído dentro do Timeline).
- AJUSTADO a pedido do usuário — marcador passou de círculo com contorno colorido pra círculo PREENCHIDO com a cor do tone, ícone em branco (semantic.texto-invertido) por dentro. Quando items[].icon não é fornecido, um ícone padrão por tone entra no lugar (success=check, warning=warning-circle, error=x-circle, info=info) — só tone='neutral' sem icon mantém o pontinho branco decorativo original, já que não existe um glyph 'neutro' óbvio. ### TimePicker

- Duas colunas roláveis (Hora 00–23 / Minuto 00–59 por step) em vez de uma lista única de horários pré-combinados (ex.: '08:00', '08:30', '09:00'...) — colunas separadas cobrem qualquer combinação real (inclusive minTime/maxTime cortando ambas as pontas) sem precisar gerar e rolar uma lista potencialmente longa de combinações prontas.
- Popover NÃO fecha automaticamente ao escolher só a hora ou só o minuto — fecha por dismiss (clique fora/Esc), diferente do DatePicker (que fecha ao clicar um dia, porque um dia já é o valor completo). Escolher hora e depois minuto são duas ações separadas dentro da mesma interação; fechar cedo demais obrigaria reabrir o popover no meio do fluxo.
- step (incremento da coluna de minutos) default 5 — granularidade comum o bastante pra maioria dos formulários (agendamento, horário comercial) sem virar uma lista de 60 opções por padrão; step=1 continua disponível pra quem precisa de precisão de minuto a minuto.
- Sem granularidade de segundos nesta v1 — nenhum caso de uso real do harness até agora precisa de segundos; se aparecer, é decisão nova (provavelmente uma terceira coluna).
- minTime/maxTime cortam AMBAS as colunas juntas (uma combinação hora+minuto fora do intervalo fica desabilitada mesmo que a hora isolada esteja dentro do intervalo) — mesmo racional de minDate/maxDate do Calendar, mas aplicado a um par de valores em vez de um único.
- Modo range resolvido exatamente como no DatePicker: dois campos/popovers independentes (Início/Fim), com o campo Fim aplicando minTime = value.start — reaproveita a mesma decisão já validada, sem inventar uma segunda estratégia de range só porque o valor agora é hora em vez de data.
- AJUSTADO a pedido do usuário — campo passou de <button> (só seleção pelas colunas) pra <input type='text'> com máscara automática 'HH:MM', mesma técnica e racional já aplicados no DatePicker: só dígitos aceitos, separador ':' inserido sozinho, sem ambiguidade de formato. Validação só considera o horário completo (4 dígitos): hora 0-23, minuto 0-59, dentro de minTime/maxTime — value só muda quando os 4 dígitos formam um horário válido. Blur com texto incompleto/inválido/fora do intervalo reverte pro último value confirmado.
- BUG REAL corrigido em teste no navegador (mesma causa raiz do DatePicker) — onChange/onBlur do input eram sobrescritos silenciosamente pelo spread de getReferenceProps() do floating-ui (que também define seus próprios onChange/onBlur), porque vinham ANTES do spread no JSX. Corrigido passando os handlers como argumento — getReferenceProps({ onChange, onBlur }) — que compõe em vez de sobrescrever.
- AJUSTADO a pedido do usuário — nova prop 'showPicker' (default true), mesma implementação e racional do DatePicker: hooks useClick/useFocus/useDismiss do floating-ui desabilitados via { enabled: showPicker } quando false, ícone caret-down e aria-haspopup/aria-expanded somem, digitação com máscara continua funcionando normalmente. Cobre o caso de um campo de horário só-digitação, sem o overhead das colunas de seleção.
- AJUSTADO a pedido do usuário — popover visualmente refeito: cada coluna ganhou um cabeçalho fixo ('Hora'/'Min', texto-micro-forte, fundo semantic.fundo-secundario, separado por borda) pra deixar claro o que cada coluna representa sem depender só do aria-label; as opções passaram de retângulos finos ocupando a largura toda pra círculos de 40px centralizados (raio-circular), mais parecidos com o padrão visual de um relógio/seletor de hora e com alvo de clique mais confortável; o popover ganhou box-shadow (structural.sombra-p) além da borda que já tinha. Motivo: o layout anterior (colunas estreitas, sem cabeçalho, sem sombra) lia como uma lista crua em vez de um componente de seleção — o usuário classificou como 'esteticamente feinho'.
- AJUSTADO a pedido do usuário — fundo do campo trocado de semantic.fundo-superficie pra semantic.fundo-campo (token novo): 'o fundo dos inputs de forma geral, devem ser levemente mais escuros que a cor de fundo da página onde estão, para destacar melhor'. No modo claro fundo-campo é idêntico a fundo-superficie (sem mudança visual, branco com borda já bastava) — só no modo escuro os dois valores divergem (fundo-campo um degrau mais escuro que a página), porque era só ali que o campo ficava indistinguível da própria página por trás.
- AJUSTADO a pedido do usuário — novo Icon 'clock' fixo à esquerda do trigger (registro fechado do Icon ganhou esse nome, Phosphor Clock), com nova prop showIcon (default true) pra permitir escondê-lo. Antes o TimePicker não tinha ícone nenhum à esquerda (só o caret-down à direita) — mesmo pedido de uma vez pros três pickers de data/hora do harness (ver decisions do DatePicker), pra dar a mesma pista visual 'isso é um campo de horário' que o DatePicker já tinha, mas de forma opcional desde o início.
